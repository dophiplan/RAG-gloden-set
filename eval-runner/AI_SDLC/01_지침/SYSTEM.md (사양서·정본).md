# SYSTEM.md — 골든셋 파이프라인 전체 명세

> 이 문서는 시스템이 **무엇으로 구성되고 어떻게 흐르는가**를 정의한다.
> 모든 동작은 `knowledge/CONSTITUTION.md`(헌법)를 따른다. 충돌 시 헌법 우선.
> 개발 순서·합격 기준은 `ROADMAP.md`, 개발 착수 지시는 `BUILD_INSTRUCTIONS.md` 참조.

---

## 1. 시스템이 하는 일 (한 문장)

제품별(RC·RV·RM·HR) RAG 원문으로부터 골든셋을 **생성→검증→확정**하되,
사람은 **설계 승인·최종 확정·충돌 판정** 3곳에서만 개입하고, 나머지는 자동 또는 외부 핸드오프로 흐른다.
모든 단계는 로그를 남기고, 막힌 것은 학습 루프(헌법 §6)로 시스템을 개선한다.

---

## 2. 노드 구성 (파이프라인)

```
[원본 입력] → [1.커버리지맵] → ✋[설계 승인] → [2.생성]
   → [3.1축 verifier(자동)] → 🔄[4.2축 검증] → 🔄[5.3차 분류]
   → ✋[6.최종 확정] → [검증완료 골든셋]
```

노드 타입 3종:
- **자동(AUTO)**: 판단 없는 노동. 코드가 수행. (1축, 집계, 출처채움, 배치분할)
- **핸드오프(HANDOFF 🔄)**: 생성과 다른 AI에 파일을 내보내고 결과를 받음. (2축, 3차) — 헌법 §2.1
- **사람 게이트(GATE ✋)**: 사람만. (설계 승인, 최종 확정, 충돌 판정) — 헌법 §2.4
- **에이전트(AGENT)**: 사람과 대화하며 수행. (커버리지맵, 생성)

## 3. 노드별 명세

> 각 노드는 `agents/`의 해당 정의를 두뇌로 쓴다. 아래는 입출력·로그 규약.

### 노드 1 — 커버리지맵 (AGENT)
- 담당 에이전트: `agents/agent_coverage.md`
- 입력: 제품 원본 코퍼스(`{제품}/원본/`), 커버리지맵 작업지시서 v0.4(고정 키트)
- 출력: `{제품}/coverage_map.xlsx` (21컬럼: Unit ID·acl_level·citation_id·related_units 등)
- 로그: 단위 수, 분해 기준, 미검토/커버/사람확인 분포
- 헌법 연결: §2.5(미검토≠보류), §2.7(citation_id), §2.8(동질 묶음)

### ✋ 게이트 — 설계 승인
- 담당: 사람 + `agents/agent_gate.md`
- 사람이 정함: 커버 목표(%) · 유형/난이도 배분 · 단위 묶음 기준 · 충돌 처리 방침
- 출력: `{제품}/design_approval.md` (승인된 방침)
- 헌법 연결: §2.4

### 노드 2 — 생성 (AGENT)
- 담당 에이전트: `agents/agent_generate.md`
- 입력: coverage_map + 원본 + 생성규칙서·SOP(고정 키트) + 승인된 설계
- 출력: `{제품}/goldenset_draft.xlsx` (스키마 = DATA_SCHEMA.md, 검증상태=초안)
- 로그: 배치별 문항 수, 유형/난이도 분포, 커버율, 발견된 충돌
- 헌법 연결: §2.6(verbatim), §2.7(citation), §2.8(억지금지), §3.7(F형 권한), §4(스키마, answer_type 포함)

### 노드 3 — 1축 verifier (AUTO)
- 담당: 도구 `verifier/`(공백무시본, 고정 키트). 에이전트 아님.
- 입력: goldenset_draft + 원본 코퍼스
- 출력: `{제품}/verify_1axis.json` (status별: e_trap/ok_uncited/partial/missing + found_in)
- 자동 후처리: e_trap→완료, ok_uncited→커버리지맵으로 출처 자동 채움→완료, partial·missing→사람볼것 분리
- 로그: status 분포, 자동완료 건수, 사람볼것 건수
- 헌법 연결: §2.2(1축=스크립트), §3.1(completed=0 오판 금지), §3.3(공백무시)

### 🔄 노드 4 — 2축 검증 (HANDOFF)
- 담당: `agents/agent_handoff_2axis.md`
- 시스템이 자동 생성: 검증할 입력(jsonl, 배치 자동분할) + 표준 judge 프롬프트(고정 키트) + 핸드오프 안내
- 사람이 함: 그 파일을 **생성과 다른 AI**(Claude 새 세션/GPT 등)에 돌려 결과를 가져옴 — 헌법 §2.1
- 입력 받음: 외부 판정 결과(JSON: id/verdict 타당·의심·반려/checks/reason)
- 시스템이 자동: 결과 집계 → 다음 노드로
- 로그: 배치 수, 어느 AI에 돌렸는지, 타당/의심/반려 분포
- 헌법 연결: §2.1(자기검증 금지), §3.4(다중정답≠충돌, answer_type 분기)

### 🔄 노드 5 — 3차 분류 (HANDOFF)
- 담당: `agents/agent_handoff_3rd.md`
- 시스템이 자동 생성: 2축 결과 + 3차 교차검토 프롬프트(고정 키트) + 핸드오프 안내
- 사람이 함: 또 다른 AI 세션에 돌려 결과를 가져옴
- 입력 받음: 분류 결과(A 사람즉시검토 / B 경미 / C 통과후보 / ★역검출)
- 로그: A/B/C/역검출 건수
- 헌법 연결: §2.1, §3.7(F형 같은 구조 묶음 점검)

### ✋ 노드 6 — 최종 확정 (GATE)
- 담당: 사람 + `agents/agent_gate.md`
- 사람이 봄: 3차가 추려준 A + 역검출만. 통과/교정/탈락 판정.
- 교정 지시 발생 시: 생성 에이전트(만든 주체)에게 "이렇게 고쳐"로 전달(판정 아님, 실행만)
- 출력: `{제품}/goldenset_final.xlsx` (검증상태=검증완료), 잔여는 사람확인/미커버
- 로그: 확정 건수, 교정 건수, 탈락 건수, 사람확인 잔여
- 헌법 연결: §2.4, §3.2(missing 일괄완료 금지)

## 4. 폴더 구조 (런타임)

```
goldenset-system/
├─ README.md / SYSTEM.md / ROADMAP.md / BUILD_INSTRUCTIONS.md / DATA_SCHEMA.md
├─ knowledge/        ← 헌법·미결함·판례 (학습 두뇌)
├─ agents/           ← 노드별 에이전트 정의 + 오케스트레이터 + 트리아지
├─ kit/              ← 고정 키트 (4제품 공용, 불변)
│   ├─ verifier/                       (공백무시본)
│   ├─ judge_prompt_2axis_표준.md
│   ├─ 3차_교차검토_프롬프트.md
│   ├─ 생성규칙서.md / SOP.md / 검증규칙서.md / 커버리지맵_작업지시서_v0.4.md
├─ products/         ← 제품별 데이터 (갈아끼움)
│   ├─ RC/ ├─ RV/ ├─ RM/ └─ HR/
│   │   ├─ 원본/                        (한 번 올리면 재사용 — 매번 업로드 안 함)
│   │   ├─ coverage_map.xlsx
│   │   ├─ design_approval.md
│   │   ├─ goldenset_draft.xlsx / goldenset_final.xlsx
│   │   ├─ verify_1axis.json
│   │   ├─ handoff/   (내보낼 배치 + 받은 결과)
│   │   └─ state.json (이 제품이 어느 노드까지 왔나)
├─ logs/             ← 전 노드 결정 로그 (역추적용)
└─ tools/            ← 자동 노드 구현 (검증후처리기·집계·배치분할·영향분석)
```

- **고정 키트(kit/) vs 제품 데이터(products/) 분리** = 헌법 §2.3.
- **원본 저장소(products/{P}/원본/)**: 한 번 넣으면 모든 노드가 재사용. 추가 시 영향분석 작동.

## 5. 상태·로그·역추적

### state.json (제품별)
```json
{
  "product": "RM",
  "current_node": "4_2axis_handoff",
  "nodes": {
    "1_coverage": {"status":"done","at":"...","output":"coverage_map.xlsx"},
    "2_generate": {"status":"done", ...},
    "3_verify_1axis": {"status":"done","summary":{"완료":128,"사람확인":2}},
    "4_2axis_handoff": {"status":"waiting_external","batches":10}
  },
  "human_queue": [{"node":"6_confirm","items":["RM-F09","RM-F21"]}]
}
```

### 로그 (logs/) — 모든 노드 공통 기록
한 줄에 1 결정: `시각 · 제품 · 노드 · 입력(파일/버전) · 결정 · 근거`
- 예: `2026-06-25T.. · RM · 3_verify_1axis · goldenset_draft v0.2 · 38건 missing→공백무시 재시도 통과 · §3.3`

### 역추적 (헌법: 완벽 아니라 작동 → 고쳐가며)
- 최종 산출물이 이상하면 로그를 거슬러 "어느 노드 출력부터 틀어졌나"를 찾는다.
- 노드는 독립이라 **그 노드부터 부분 재실행** 가능 (전체 재실행 아님).
- 영향분석(아래)이 "어디부터 다시"를 자동 계산.

## 6. 영향분석 (원본 추가/변경 시)

- 담당: `agents/agent_impact.md`
- 트리거: `products/{P}/원본/`에 파일 추가·수정
- 동작: citation_id 조인으로 "바뀐 원문 → 영향받는 커버리지맵 단위 → 연결된 골든셋 문항"을 추적
- 출력: "이 영역 N단위 추가/변경 → 생성 노드부터 다시(추가분만). 기존 M문항은 영향 없음" 계획 제시
- 사람이 "진행" → 영향 가지만 재실행. (헌법 §2.7 citation_id 토대)

## 7. 멀티 제품 (2층 UX)

- **층 1 — 전체 보드**: RC·RV·RM·HR 카드. 각 카드에 현재 노드·진척률·상태(🟡사람대기/🔵자동/🟢완료).
  상단 전체 지표: 진행중 / ✋사람대기 / 자동중 / 평균진척.
- **층 2 — 제품 상세**: 카드 클릭 시 그 제품의 7노드 파이프라인 펼침. 색으로 상태 표시.
- 4제품 **병렬 진행**: 각자 state.json을 가져 서로 안 막음. 사람은 "✋대기"만 처리.

## 8. 지표 (측정)

| 지표 | 정의 | 용도 |
|---|---|---|
| 커버리지율 | 커버됨 / 전체 비-TC 단위 | 제품별 진행도 |
| 단계별 진척 | 초안/1축통과/2축통과/검증완료 건수 | 병목 파악 |
| 반려·의심율 | 2축에서 걸린 비율 | 생성 품질 신호 (높으면 생성 노드 점검) |
| 사람 대기 건수 | 현재 ✋에 막힌 수 | 줄면 시스템이 잘 도는 것 |
| 미결 이슈(유형별) | OPEN_ISSUES 카운트 | 트리아지 패턴 감지 입력 |
