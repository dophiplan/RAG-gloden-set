# RAG 평가 방법론 — 골든셋·커버리지맵 설계 표준

> 목적: 신규 카테고리(제품·팀)의 문서군을 받았을 때 **무엇을 중심으로 골든셋·커버리지맵을 설계할지** 일관되게 판정하기 위한 기준 문서.
> 적용 범위: RAG 통합 평가 골든셋 생성 전 단계(범위 정의 ~ 검증). 시스템 구현(파싱·청킹·임베딩)은 별도 레이어로 본 문서 범위 밖.
> 상태: v1.4 (v1.3→v1.4: 코퍼스판 트랙 정의 명문화 — DEC-026. 코퍼스=범위·원문 확보 경로, 정답 근거=정본(DEC-011), 청크≠단위, 이중 트랙(생성 AI 상호 비공개) 후 source키 합집합 통합·ID 재부여는 도구(작업 AI) 몫)
> 상태(구): v1.3 (v1.2→v1.3: 청크 매핑 레이어 구체화 — 별도 매핑 시트·느슨/엄격 2수준 채점·사각지대 지표. 시스템팀 export 가이드와 정합) (v1→v1.1: 유형 코드를 현행 표준으로 통일 — B=통계, C=복합. 생성 규칙서 v3.3·런북 v3.2와 단일 정의) / 작성 Claude(Opus 4.8) — 표준 프로세스 추출 기준용.

## 0. 한 줄 요약

골든셋·커버리지맵은 **시스템 구현에 종속되지 않는, 원문 사실 기반의 평가 기준**이다.
문서 성향에 따라 *질문유형 분포·난이도·단위 입도·발췌 방식*은 달라지지만, *정답의 진실성·시스템 비종속 원칙*은 변하지 않는다.

## 1. RAG 평가 정석 프로세스 (6단계)

| 단계 | 내용 | 산출물 | 비고 |
|---|---|---|---|
| 1. 범위 정의 | 대상 제품·문서·사용자 경계 긋기 | 마일스톤 정의 | 카테고리(RC/RV/RM/HR…) 분리 |
| 2. 커버리지맵 | 질문 공간을 빠짐없이 덮는 지식 항목 지도 | OKF 단위 목록 | *무엇을 평가하나*의 지도 |
| 3. 골든셋 생성 | 질문·정답·발췌·유형·난이도 작성 | 골든셋 본문 | 정답=원문 사실, 시스템 비종속 |
| 4. 검증·확정 | 3주체 분리 + 2축(LLM 채점→사람 최종) | 확정 골든셋 | 자기검증 금지 |
| 5. 시스템 연결·메트릭 | 실제 RAG에 질문 투입, 검색/생성 분리 측정 | 메트릭 리포트 | ↓ 표 참조 |
| 6. 분석·개선 루프 | 약점 진단 → 청킹·임베딩·프롬프트 수정 → 재측정 | 개선 이력 | 골든셋은 고정, 시스템만 변경 |

### 5단계 메트릭 — 두 레이어로 분리 측정

| 레이어 | 메트릭 | 무엇을 보나 | 골든셋의 어느 부분이 기준이 되나 |
|---|---|---|---|
| 검색(retrieval) | context recall | 정답 근거가 검색돼 왔나 | **발췌(근거 원문)** |
| | context precision | 검색된 청크가 관련 있나 | 발췌 + 단위 매핑 |
| 생성(generation) | faithfulness | 가져온 근거에 충실한가(환각 없나) | **합격기준(Faithfulness≥4)** |
| | answer correctness / relevancy | 질문·정답과 맞나 | **정답·합격기준(Correctness≥4)** |

> 분리하는 이유: "틀린 답"이 **검색 실패**(근거를 못 가져옴)인지 **생성 실패**(근거는 왔는데 답이 틀림)인지 진단하기 위해. 합치면 원인을 못 가른다.

## 2. 두 레이어 원칙 — 왜 시스템과 안 겹쳐야 하나

- **평가 기준이 시스템 구현에 종속되면, 그 시스템이 틀렸을 때 잡아낼 수 없다.** 채점 기준이 피채점자에 묶이는 셈.
- 골든셋 정답은 **원문 사실**에 근거한다. 예: "제어모드는 Win→Mac에서 X" — 시스템이 표를 셀로 쪼개든, 행으로 긁든, 섹션 통째로 넣든 이 사실은 변하지 않는다.
- **커버리지맵 단위 ≠ 시스템 청크.** 입도가 다른 게 정상.
  - 커버리지맵 단위 = "사용자가 물어볼 수 있는 지식 항목" (평가 항목)
  - 시스템 청크 = "검색 효율을 위해 문서를 나눈 조각" (검색 단위)
- 단위가 청크보다 잘면, 5단계에서 "이 단위가 어느 청크에 있어야 하나"를 매핑하는 레이어를 한 번 둔다. **입도를 억지로 청크에 맞추지 말 것.**
- **★ 청크 매핑 레이어 규격 (v1.3):** 매핑은 골든셋 **본체 컬럼이 아니라 별도 매핑 시트**에 둔다 — `문항ID ↔ doc_key(문서 지문) ↔ point_id(청크 ID, 복수 가능)`. 이유: point_id는 재청킹 시 바뀌는 시스템 값이라, 본체에 넣으면 재청킹 때마다 시험지를 손대게 됨(종속의 뒷문). **재청킹 시 시험지 본체는 불변, 매핑 시트만 재생성**한다.
- **검색 채점 2수준:** 느슨=hit의 source_url을 doc_key로 역매핑해 문서 일치 확인(URL 변형은 doc_key로 접어 비교, URL 직접 비교 금지) / 엄격=hit id가 기대 point_id와 일치. 구버전 문서 공존 시 정답 출처는 현행 doc_key로 고정, 구버전 hit는 오답 처리(Q4 시점 장치와 동일).
- **역방향 사각지대 지표:** 골든셋이 참조한 point_id 집합 ↔ 청크 전체 대조 → 한 번도 근거가 안 된 청크 = 미커버 사각지대. 문서 수준 커버 이후의 심화 지표(청크 수준 커버리지 %).
- **★ 코퍼스 사용 원칙 (v1.2):** 실물 RAG의 코퍼스(청크) export는 **"범위·원문 확보 경로"로만** 쓴다 — **정답의 근거는 정본 원문이다.** 커버리지맵↔코퍼스 대조에서 나온 차이분은 골든셋 수정 대상이 아니라 **"인입 누락 리포트"**(별도 산출물)로 시스템 팀에 전달한다 — 이것이 6번 박스(지식 파이프라인) 평가다. 코퍼스 버전은 시험지가 아니라 **성적표(평가 회차) 메타데이터**에 기록한다. **정본에는 있으나 코퍼스에 인입되지 않은 내용의 문항도 시험지에 포함한다**(사용자 확정 2026-07-07) — 그 실패가 곧 인입 누락의 점수화다. 단 성적표에서 해당 문항을 **"인입 누락 기인" 태그로 분리 집계**해 엔진 결함과 구분한다.

### 청킹이 문서마다 달라지는 것 vs 골든셋이 달라지는 것

- "청킹이 바뀌었으니 골든셋도 바꾼다" → **틀린 연결.** 평가가 시스템을 따라가 무의미해진다.
- 다만 둘 다 "문서 성향을 읽는다"는 태도는 공유한다. 골든셋도 *그 문서에서 뭐가 평가 가치가 큰가*에 따라 설계가 달라진다.
- **결론: 같은 문서에서 청킹과 골든셋이 둘 다 달라지지만 이유가 다르다.** 하나는 검색 최적화, 하나는 평가 설계.

## 3. 문서 성향별 평가유형 매핑표

문서가 품은 지식의 성격에 따라 권장 유형 분포·단위 입도·발췌 방식이 달라진다.

| 문서 성향 | 평가 가치의 핵심 | 권장 유형 강조 | 단위 입도 | 발췌 방식 | 사례 |
|---|---|---|---|---|---|
| **매트릭스 표** | 비대칭·경계(어디서 안 되나) | G(경계)·C(복합) ↑, A ↓ | 기능 1개 = 1단위 | 기능명 셀(O/X 단독셀 미사용) | RC 제품 기능표 |
| **사양·버전** | 사실 정확성 + 버전 컷오프 | A(사실확인) ↑ + 버전 G | 사양 항목 단위 | 사양값 셀 | RC 사양·호환성 |
| **절차 매뉴얼** | 순서·조건·선후관계 | D(멀티홉) ↑, A·C | 절차 스텝 단위 | 단계 설명 문장 | RC 매뉴얼(예정) |
| **FAQ/헬프데스크** | 실제 사용자 질문 형태 | 자연어 질문 다양성 ↑ | Q–A 쌍 | 답변 핵심 문장 | 헬프데스크 아티클 |
| **정책/거버넌스** | 권한·금지·예외·미규정 | F·E·D·G ↑, A ↓ | 조·호 단위 | 조항 문구 | 인사팀·회계팀 규정 |

> 유형 코드(현행 표준 — 생성 규칙서 v3.3 §3.2와 동일): A=단순조회 / B=통계·수치집계 / C=복합(한 문장에 2개+ 질문) / D=멀티홉 / E=무응답함정 / F=권한·거버넌스 / G=경계·예외

## 4. ★ 카테고리 중심 잡기 — 판정 절차 (재사용 체크리스트)

**신규 문서군을 받으면 이 5문항을 순서대로 돌린다.** 산출은 맨 아래 한 줄.

### Q1. 문서 종류가 갈리나, 균일한가?
- **갈린다**(매뉴얼·사양서·표 등 종류가 다름) → 중심이 **"문서"**다. 평가 가치가 큰 문서 종류를 중심으로 잡는다. (예: RC = 기능표·사양서·매뉴얼)
- **균일하다**(전부 규정·조항 등 한 성격) → 중심이 **"평가 유형"**으로 옮겨간다. "어느 문서"가 아니라 "무엇을 묻나"가 축. (예: 인사팀 = 전부 정책)

### Q2. 평가 가치가 어디 있나? (복수 선택)
문서를 훑으며 어느 쪽 소재가 많은지 본다 → 권장 유형 분포 결정.
- 단순 사실·값 조회가 많다 → **A**
- "되고/안 되고"의 조건·예외·경계가 많다 → **G**
- 둘 이상을 견줘야 하는 게 많다 → **C**
- 여러 항목/조항을 엮어야 결론이 나온다 → **D**
- "규정에 없음"이 의미 있는 답이 된다 → **E**
- 권한·금지·의무·승인 주체가 핵심이다 → **F**

### Q3. 충돌 시 기준이 되는 정본(authority)이 있나?
- 문서 간 위계가 있나? (상위 규정 > 세칙 > 가이드/FAQ)
- 충돌 시 어느 문서가 이기나? → 그게 **중심 정본**.
- 정본이 미수령/부재면 → 그 위에 세운 답은 흔들림. **"자료부족"으로 명시 처리**하고 정본 확보를 사람확인으로.

### Q4. 시점(version) 민감도는?
- "현행이 무엇이냐"가 자주 바뀌나?
- 바뀐다면 → 정답에 **기준 시행일/버전을 박고**, 정본 개정 시 해당 문항을 재검토 대상으로 표시.
- (정책 문서는 사양서보다 시점 장치가 더 중요.)

### Q5. 발췌(근거)를 어디서 따나?
- 표 → 의미 단위 셀(값 단독셀은 발췌 가치 없음, 셀 행 합치기는 재배치 금지)
- 산문/조항 → 근거 문장 연속 문자열 그대로
- 원문이 외부(웹 URL 등)라 확보 불가 → **사람확인 대상**으로 분리

### → 산출 (한 줄로 정리)
```
[카테고리]: 중심축 = (문서 X / 평가유형 Y)
            권장 유형 분포 = A__ G__ C__ D__ E__ F__
            단위 입도 = ____
            중심 정본 = ____ (없으면 자료부족 명시)
            시점 장치 = (필요/불요)
            발췌 방식 = ____
```

## 5. 적용 사례 (이미 수행한 것)

### 사례 A — RC 제품 기능표 (매트릭스 표)
- Q1: 종류 갈림 → 문서 중심. 그중 기능표는 매트릭스.
- Q2: 비대칭·경계가 핵심 → G·C ↑, A ↓
- 산출: 중심축=문서(기능표) / 유형 A40 G32 C·D12 E16 F0 / 입도=기능 1개 / 발췌=기능명 셀 / 시점=불요
- 특이: 규칙적 X(Linux 전부)는 대표 묶음, 비대칭 X(Win→Mac만, Mac→만 O 역전 등)는 직접 커버.

### 사례 B — RC 사양·호환성 (사양·버전)
- Q2: 사실 정확성 + 버전 컷오프 → A ↑ + 버전 G
- Q3: 문서 내부 충돌 발견(iOS15 표 O vs 비고 spec out 등) → 충돌목록·사람확인 분리
- 산출: 중심축=문서(사양서) / A 우세 / 입도=사양 항목 / 시점=필요(버전)

### 사례 C — 인사팀 (정책/거버넌스)
- Q1: 균일(전부 정책) → **중심축이 평가유형으로 이동**
- Q2: 권한·예외·미규정 → F·E·D·G ↑
- Q3: 취업규칙 등 정본 미수령 → **"자료부족" 명시**, 정본 확보 대기
- Q4: 시점 민감 높음 → 시행일 기준 박기
- 특이: 민감 단위 플래그, 충돌·근거약함 검토대상 분리.

## 6. 불변 원칙 (문서 성향과 무관)

1. **정답은 원문 사실에 근거** — 시스템 파싱 방식과 독립.
2. **생성/검증/확정 3주체 분리** — 자기검증 금지.
3. **2축 검증** — LLM 채점 우선 + 사람 최종.
4. **발췌는 근거 위치 표식** — 정답 전체가 아니라 검색 평가용 대조점.
5. **억지 금지** — 분포 숫자 맞추려 동질 문항 양산하거나 예외를 쳐내지 않음. 커버는 정직하게(대표 묶음의 측면 한정은 작업보고에 명시).
6. **모르면 자료부족** — 근거 없으면 지어내지 않고 명시·에스컬레이션.
