## 0. 검증에 필요한 3종 (이게 없으면 검증 불가)

1. **이 검증 규칙서** — 검사 방법
2. **검사할 골든셋 파일**(들) — 1개를 검사하거나, 여러 개를 비교
3. **원본 자료 전체**(PDF·엑셀·규정 등) — 발췌를 대조할 원본. **이게 핵심.**
   원본이 없으면 발췌 진위·커버리지를 확인할 방법이 없다.

> ★ 여러 모델/세션에 검증을 맡길 때, **골든셋만 주지 말고 원본 자료를 반드시 함께 줘라.**
> 원본 없는 검증은 "발췌가 진짜인지" 확인 못 해 무의미하다.

## 1. 검증의 3개 축 (무엇을 확인하나)

골든셋은 모든 평가의 "잣대"라, 잣대가 틀리면 모든 평가가 틀어진다. 세 가지를 본다:

1. **발췌 진위** (넣은 게 진짜냐): '근거 원문 발췌'가 실제 원문에 그대로 있는가? (AI가 지어낸 가짜 발췌 차단)
2. **정답 정합성** (정답이 과장 안 됐나): '정답'이 그 발췌로 뒷받침되는가? 발췌를 넘어 왜곡·과장되지 않았는가?
3. **★ 커버리지 (빠뜨린 게 없나, v2.0 신설)**: 문서의 의미 단위가 골든셋에 빠짐없이 반영됐는가?

> v1.0은 1·2만 봤다(넣은 것 검사). 그래서 "띄엄띄엄" 누락을 못 잡았다. v2.0은 3을 추가한다.

## 2. 발췌 진위 — 문자 대조 (1축)

### 2.1 방법
- '근거 원문 발췌' 텍스트가 원문 자료에 문자열로 존재하는지 검색.
- 존재하면 OK, 없으면 '발췌 의심' 플래그.
- **LLM 판단이 아니라 코드(문자 매칭)로 한다.** "확인해줘"라고 물으면 비슷한 걸 관대하게 통과시킴.

### 2.2 ★ 문자 대조 시 반드시 처리할 함정 (안 하면 거짓 경보)

1. **특수 따옴표·기호**: 원문 PDF엔 특수문자(ʻ ʼ ' ' " ")가 많다. NFKC 정규화로 일반화/제거.
2. **공백·줄바꿈**: PDF 추출 시 공백이 원문과 다름. 대조 시 **모든 공백 제거** 후 비교.
3. **표 기호**: ○ ● △ - | 같은 기호 섞인 발췌는 기호·공백 제거 후 핵심 텍스트로 비교.
4. **말줄임(…)**: 발췌에 "…"가 있으면 그 자리에서 끊고 앞뒤 조각을 **각각** 원문에서 찾는다.
5. **여러 파일은 따로 검색**: 원문이 여러 파일이면 합치지 말고 **파일별로** 검색(경계에서 문장 잘림 방지).
6. **잘린 셀 주의**: 엑셀 추출은 셀이 잘릴 수 있다. 안 잡히면 '가짜' 단정 말고 '원본 셀 확인 필요'로.
7. **★ 텍스트 추출 자체가 안 되는 문서**: 스캔본·이미지 PDF는 문자열이 아예 안 나온다. 이때 발췌가 원문에 "없다"고 단정하면 **틀린다(가짜가 아니라 확인 불가)** → '원본 추출 불가 — 사람 육안 대조'로 분류. (실제로 발생한 사례: 이미지 PDF·비교표가 추출 안 됨. 4.4와 함께 처리.)

### 2.3 조합(멀티홉·표) 문항 처리
- 생성 규칙서 2.1대로 조합 문항은 발췌가 여러 개다. **각 발췌를 각각** 원문 대조.
- 하나라도 원문에 없으면 그 문항은 '발췌 의심'.

## 3. 정답 정합성 (2축)

### 3.1 무엇을 보나
- "이 발췌가 이 정답을 뒷받침하는가?"를 확인.
- 발췌에 없는 내용이 정답에 들어가 있으면 플래그.
  - 예: 발췌엔 "지원"만 있는데 정답에 "단 macOS 제외"가 붙어 있으면 → 그 단서의 출처를 따로 확인.
- 조합 문항은 "여러 발췌를 연결한 결론이 타당한가"를 본다 (논리 비약 없는지).

### 3.2 ★ 어떻게 검사하나 — 방법·역할 분담 (v2.2 신설)

1축은 위조 탐지라 코드 문자 대조로 끝나지만, **2축은 "발췌가 정답을 과장·날조 없이 뒷받침하나"라는 의미 판단**이라 코드로 못 끝낸다. 그렇다고 "확인해줘"라고 통째로 물으면 관대하게 통과된다(2.1과 같은 함정). 그래서 **LLM 1차 + 사람 최종** 구조로, 조각 단위로 본다.

**(A) LLM/스크립트가 하는 1차 대조**
- 정답을 **원자 단위로 쪼갠다**(주장 하나씩). "전체적으로 괜찮아 보여" 식 뭉뚱그린 판정 금지 — 조각마다 따로 본다.
- 각 조각이 **발췌의 어느 부분으로 뒷받침되는지** 짚는다. 뒷받침할 근거가 발췌에 없는 조각은 **"근거 없음"으로 콕 집어** 표시.
- **보수적으로**: 애매하면 통과시키지 말고 플래그.
- 조합 문항은 발췌들을 이은 결론에 논리 비약이 없는지 본다.
- 출력 형식: 문항별 `정합 OK` / `의심 (+ 근거 없는 조각 목록)`.

**(B) 사람만 할 수 있는 것**
- **엄격도 기준 결정**: "발췌에 없는 단어가 하나라도 있으면 플래그" vs "명백한 환언은 허용" — 이 선은 사람이 정한다. *(권장 기본값: 보수적 = 조각이라도 근거 없으면 플래그)*
- **플래그 최종 판정**: LLM이 "근거 없음"이라 띄운 조각이 — *진짜 날조*라 빼야 하는지, *맞는 내용인데 발췌만 빠진 것*이라 발췌를 보강해야 하는지는 **원문 전체·업무 지식을 아는 사람만** 가린다. (LLM은 이 둘을 구분 못 함)
- **표본 점검(검사기 점검)**: `정합 OK`로 통과된 것 중 일부를 사람이 직접 원문과 대조 → LLM이 게으르게 과장된 답을 통과시켰는지 확인 (6.2 표본 검증과 함께).

> ★ **자기검증 금지(9장)는 2축에도 적용.** 골든셋을 만든 바로 그 모델/세션이 자기 2축을 보면 안 된다. (A)는 만든 주체와 **다른 모델/세션**이 수행한다.

### 3.3 ★ 다중 정답 처리 (v2.3 신설 — RAG 시스템 필수)

실제 시스템(특히 RAG)에선 정답이 하나가 아닐 때가 많다. "휴가 신청 어떻게?"는 *그룹웨어로도, 인사시스템으로도* 다 맞는다. 골든셋에 정답을 하나만 적어두면, 다른 맞는 답을 한 모델을 **틀렸다고 잘못 채점**한다. 그래서 문항마다 **정답 유형 딱지**를 붙인다.

| 유형 | 뜻 | 처리 |
|------|----|------|
| `single` | 정답이 사실상 하나 (예: 연차 = 15일) | 기존대로 정답 1개 |
| `multi_equivalent` | 여러 답이 **다 진짜 맞음** (예: 신청 경로 2가지) | **정답 목록**으로 관리 |
| `conflict_unresolved` | 하나만 맞는데 **아직 안 가림** (예: A=15일, B=20일) | **목록에 넣지 말 것.** 6.1 '충돌'로 보내 사람이 먼저 가린다 |

> **★★ 가장 중요한 가드 — "다중 정답"과 "충돌"을 절대 섞지 마라.**
> 다중 정답은 *둘 다 맞는 것*이고, 충돌은 *하나만 맞는데 안 가린 것*이다.
> 충돌을 "정답 둘 다"로 넣으면 → **틀린 답을 말한 모델도 합격**해 채점표 자체가 망가진다(정답 부풀리기 사고).
> "둘 다 진짜 맞나?"를 먼저 확인하고, 확신이 없으면 `multi_equivalent`가 아니라 `conflict_unresolved`다.

**다중 정답 등록 형식 (각 답이 자기 근거를 들고 있어야 함):**
```json
{
  "question": "휴가 신청은 어떻게 하나요?",
  "answer_type": "multi_equivalent",
  "acceptable_answers": [
    { "text": "그룹웨어 접속 후 신청",     "source": "[GW-Rev3] 5조", "excerpt": "…원문 그대로…" },
    { "text": "인사시스템 휴가 메뉴 이용", "source": "[HR-Rev2] 3조", "excerpt": "…원문 그대로…" }
  ]
}
```
- **목록 안의 모든 답에 1축(발췌 진위)·2축(정합성)을 똑같이 건다.** 근거 없는 답은 목록에 못 들어온다(부풀리기 차단).
- **채점 방식이 바뀐다**: `single`은 "정답 하나와 일치", `multi_equivalent`은 "**목록 중 하나와 의미상 일치**"로 본다. (이 의미 일치 판정도 2축처럼 LLM 1차 + 사람 표본 점검)
- `conflict_unresolved`는 골든셋 본문에 넣지 않는다 → 사람 확인.

## 4. ★ 커버리지 누락 검사 (3축, v2.0 신설)

> 커버리지맵 작업지시서 v0.4 Layer 1의 단위 인벤토리를 검사 단계에서 재확인한다.

### 4.1 방법
1. **원문의 의미 단위 목록을 (기계적으로) 다시 뽑는다.** 생성 때 만든 커버리지 맵을 그대로 믿지 말고,
   원문에서 단위를 독립적으로 재추출해 대조한다. (생성자가 단위 자체를 빠뜨렸을 수 있으므로)
2. **골든셋 문항의 `citation_id`(=커버리지 Unit ID)와 결정 조인** → 각 단위가 덮였는지 표시.
   - ★ **6번 칸 파싱 (생성 규칙서 v3.2 §4 형식 규격):** 6번 칸을 세미콜론(`;`)으로 잘라 **왼쪽**만 취하고, 그 안을 `+`로 split해 citation_id 리스트를 얻는다(오른쪽은 사람용 출처 코드라 조인에 쓰지 않는다). 이 파싱이 결정적이라야 조인이 결정적이다.
   - ★ 휴리스틱(주제 일치)이 아니라 **Unit ID 결정 조인**이 1차다. citation_id가 비어 있거나(6번 `;` 왼쪽이 빔) 깨진 문항은 source 키(source/resource + source_location)로 보조 매칭하고, 그래도 안 붙으면 '근거 연결 누락'으로 플래그.
3. **빈 단위 확인** → 상태값과 사유가 적혀 있나 본다. (v0.4 9종 기준)
   - 사유 달린 `미커버` / `자료부족` / `근거약함` → OK (의도적 비채움)
   - **사유 없는 빈 단위(상태 `미검토`인 채 방치) → '누락 의심' 플래그** (생성자가 못 보고 지나친 것)
4. **단위 묶음 점검**: 생성자가 의미를 잘못 끊었는지(주화자모드↔50명을 따로 둠 등) 확인.
5. **`related_units` 점검**: cross-group 연결(TC↔Spec, KnownIssue↔절차)이 적힌 단위는 대상 Unit ID가 실재하는지 확인. 재분해로 끊긴 링크는 source 키로 재유도(작업지시서 3장).

### 4.2 한계
- 커버리지는 "원문 안의 단위"만 본다. 원문에 없는 사용자 실전 질문은 이 검사로 못 잡는다.
- 단위 재추출도 사람/코드가 하므로, 묶음 판단 차이가 있을 수 있다 → 6장 사람 확인 대상.

### 4.3 ★ 커버리지 충족률 계산식 (보고용 — 정의 고정)

보고에 "충족률"을 적을 때 사람마다 다르게 계산하지 않도록 식을 고정한다:

```
충족률 = 커버된 단위 수 / (전체 단위 수 − 정당한 보류 단위 수) × 100
```

- **분모에서 "정당한 비채움"은 뺀다.** = v0.4 상태 중 **사유 달린 `미커버`·`자료부족`·`근거약함`**(목적·정의·부칙 등 시험 가치 낮아 의도적으로 안 만든 것). 기존 용어 "정당한 보류"가 이것이다(계산식은 불변).
  → "문항 만들 가치가 있는 단위" 중 몇 %를 덮었는지를 보는 것이 목적이기 때문.
- **사유 없는 빈 단위(상태 `미검토` 방치 = 누락 의심)는 분모에 포함**한다. (덮었어야 할 것을 안 덮은 것이므로 충족률을 깎아야 함)
- 예: 전체 단위 30, 정당한 비채움 5, 커버 22, 누락 의심 3 → 22 / (30−5) = 22/25 = **88%**
- 보고에는 충족률과 함께 **누락 의심 단위 목록**을 반드시 같이 적는다(숫자만으론 어디가 빈지 모름).

### 4.4 ★ 추출 불가 문서 처리 (스캔본·이미지 PDF·번호 없는 줄글) — v2.1 신설

규칙은 "단위를 기계적으로 뽑는다"(4.1·생성 규칙서 5조)고만 적혀 있으나, **추출이 안 되는 문서를 만나면 그 지시가 무력**해진다. 처리 규칙을 고정한다:

1. **텍스트 추출 불가 문서(스캔 PDF·이미지 PDF)**: 단위를 기계적으로 못 뽑는다.
   → 커버리지 **분모(전체 단위)에서 제외**하되, **"추출 불가로 제외"임을 커버리지 맵·보고에 반드시 명시**한다.
   (조용히 빼면 진짜 누락과 구분이 안 된다. "안 덮음"이 아니라 "도구로 못 봄"임을 남겨야 한다.)
2. **번호 없는 줄글 안내문**: 단위 경계가 애매하다(무엇으로 자를지 막연).
   → **단락 또는 소제목 단위로 끊고, 끊은 기준을 보고에 적는다**(다른 사람이 같게 재현할 수 있도록).
3. **추출 불가 문서가 평가에 중요하면**: 자동 커버리지엔 안 잡히므로, **사람 육안으로 단위를 뽑아 별도 표기**하고 6장 사람 확인 대상으로 보낸다.
4. 위 1·2·3은 모두 **충족률 분모 계산(4.3)에서 "도구 한계로 제외"로 별도 표기**한다(정당한 비채움과도 구분).

### 4.5 ★ TC 층화 표본 처리 (전수 대상이 아님) — v2.4 신설

커버리지맵 작업지시서 v0.4는 **TestCase(TC)를 전수 분해하지 않고 층화 표본만 단위화**한다(분량 압살 방지). 그래서 TC는 4장 커버리지 검사의 "전수 대조" 대상이 아니다. 처리 규칙:

1. **TC 단위는 "전체 단위(분모)"에 전수로 넣지 않는다.** 표본 설계(`TC_표본설계_{PREFIX}.md`의 기능군·우선순위·유형별 비율·표본 수)에 따라 **표본으로 뽑힌 TC 단위만** 분모에 포함한다.
2. **표본에서 의도적으로 빠진 TC 단위를 '누락 의심'으로 플래그하지 마라.** 그건 누락이 아니라 표본 설계상 제외다. 충족률 분모에서 **"표본 설계 제외"로 별도 표기**한다(추출 불가 4.4, 정당한 비채움과 모두 구분되는 제3의 카테고리).
3. **대신 검사할 것: 표본의 대표성.** 전수 누락 대신, 표본이 설계서의 (a)기능군 분포 (b)우선순위 비율 (c)유형별(정상/예외/경계) 비율을 실제로 충족했는지 본다. 충족 못 하면 '표본 편향' 플래그 → 사람 확인.
4. **TC 표본 설계가 미정이면** TC 충족률은 산출하지 않고 보고에 "표본 파라미터 미정 — TC 검증 보류"로 명시한다.
5. 非TC 원천(사양서·매뉴얼·KnownIssue·FAQ·Helpdesk)은 종전대로 **전수 대조**(미검토 0 목표) 그대로 적용.

> 정리: 충족률 분모에서 단위는 네 갈래로 분류된다 — ① 커버 대상(정상) ② 정당한 비채움(미커버/자료부족/근거약함, 분모 제외) ③ 도구 한계 제외(추출 불가, 4.4) ④ **표본 설계 제외(TC, 4.5)**. ②③④는 "안 덮음(누락)"과 명확히 구분해 보고한다.

## 5. ★ 여러 골든셋 비교·채택 (v2.0 신설 — "3개 받았을 때")

> 여러 모델/세션이 같은 자료로 각자 만든 골든셋 N개를 받아, 비교하면서 채택/탈락한다.
> **이 과정이 곧 "하나로 합치는" 것이다.** 별도 합본 단계가 아니라 검증의 결과물이다.

### 5.1 비교의 단위 = "같은 것을 묻는 문항"끼리 묶기
- ★ **1차 묶음 키 = `citation_id`(=커버리지 Unit ID).** 모델이 다르게 출제했어도 **같은 커버리지 단위를 인용하면 같은 문항군**이다. 이건 결정적이라 휴리스틱보다 우선한다(작업지시서 v0.4 citation_id 조인). citation_id는 4.1과 동일하게 6번 칸을 `;`로 잘라 왼쪽을 `+` split해 얻는다(생성 규칙서 v3.2 §4 형식 규격).
- citation_id가 비었거나 모델이 안 단 경우에 한해 **보조로** "문맥(주제) 일치 + 정답값 일치" 휴리스틱을 쓴다. 즉 질문 문구 일치가 **아니라** 단위 동일성이 기준.

> **★★ 행 번호(위치)로 비교하지 마라 — 치명적 오류 경고**
> 모델마다 문항 순서가 제각각이다. **A의 N번 문항과 B의 N번 문항은 아무 관계가 없다.**
> 예: A의 5번="연차 며칠?"(15일), B의 5번="경조금 얼마?"(50만원) — 위치만 같을 뿐 완전히 다른 질문.
> "1열은 1열끼리, 2행은 2행끼리" 식의 **위치 기반 비교는 전혀 다른 질문을 비교하는 것**이라 결과가 통째로 무의미해진다.
> 반드시 **모든 문항을 펼쳐놓고 주제·정답 내용으로 짝을 찾아** 묶는다.
> (같은 주제 문항이 A는 5번, B는 12번, C는 3번에 흩어져 있을 수 있다 — 내용으로 찾아 모은다.)

### 5.2 ★ 정답값 정규화 (표기 차이 흡수) — 비교 전 필수 처리
모델마다 정답 표기가 다르다: "15일" / "15" / "15개" / "휴가 15일" / "15일입니다".
이걸 글자로 비교하면 다 "다름"이 되어 다수결이 깨진다. 비교 전에 정규화:

- **숫자+단위 핵심값만 추출**: "15일"="15"="15개"="휴가 15일" → 핵심값 `15`(+단위 '일')
- 조사·군더더기·공백·"~입니다"·"약" 등 제거
- 그 후 핵심값으로 비교
- ★ **복합·조건부 답은 숫자를 '집합'으로 뽑는다** (v2.2): "정규직 15·계약직 10"은 `{15,10}`, "15일"은 `{15}`. 집합이 다르면 다른 답으로 본다. (부분 숫자만 집어 "15"끼리 잘못 일치시켜 불완전한 답을 채택하는 사고 방지)

### 5.3 ★ 문맥 일치 먼저 확인 (엉뚱한 일치 방지)
숫자만 같다고 같은 문항이 아니다. **주제가 같은지 먼저 본다.**
- 예: "연차 15일"과 "병가 15일" → 둘 다 `15`지만 **완전히 다른 문항**. 묶으면 안 됨.
- 따라서 채택 판정은 **"문맥(주제) 일치 AND 정답값 일치"** 일 때만.

### 5.4 채택/탈락 규칙

| 상황 | 판정 | 보내는 시트 |
|------|------|-----------|
| 2개 이상 모델이 **문맥 일치 + 정답값 일치**(정규화 후) | **채택** | 골든셋 본문 |
| 문맥은 같은데 **정답값이 다름** | 사람 확인 (왜 갈렸는지 = 각 발췌 출처를 함께 기록) | 사람 확인 |
| **단독 문항**(한 모델만) + 발췌 진위 통과 | 후보 보존 | **번외 질문** |
| **단독 문항** + 발췌 진위 실패/의심 | 진위 확인 필요 | 사람 확인 |

- "2개 이상 일치"가 다수결 기준이다. (모델 3개 기준 2:1 이상)
- 일치해도 모든 모델의 **발췌가 다 의심**이면 채택하지 말고 사람 확인.

### 5.5 다수결의 한계 (정직하게)
- 다수결은 "넣은 문항이 맞나"는 잘 거른다. 그러나 **여러 모델이 똑같이 어떤 단위를 안 본 누락은 못 잡는다.**
- 그 누락은 4장 커버리지 검사(원문 단위 재추출 대조)로만 잡힌다. → 5장과 4장을 **둘 다** 해야 한다.

## 6. 판정 분류와 사람 확인

### 6.1 각 문항을 분류
- **OK**: 발췌 진위 통과 + 정답 정합 + (비교 시) 다수결 채택 → 골든셋 본문
- **사람 확인**: 발췌 자동대조 실패(단, 2.2 함정 가능 → '가짜' 단정 말 것) / 정답 과장 / 정답값 충돌 / 단독+진위실패
- **번외 질문**: 단독 문항 + 진위 통과 (틀린 게 아니라 다수결 미경유)
- **충돌**: 자료 A·B가 다름 → 충돌 목록, 제품·규정팀 판정. (3.3의 `conflict_unresolved`도 여기로 — "정답 둘 다"로 위장하지 말 것)
- **다중 정답**: 여러 답이 다 맞음(3.3) → 정답 목록으로 본문에 등록 (각 답이 1·2축 통과해야 함)
- **누락 의심**: 보류 사유 없는 빈 단위 → 생성자에게 보강 요청

### 6.2 사람만 할 수 있는 것 (자동화 불가)
- **충돌 판정**: 자료끼리 다를 때 어느 쪽이 맞는지 (제품·업무 아는 사람만)
- **버전 최신성**: 개정 시행 여부 등 (회사 사람만)
  - ★ **개정 감지·정기 점검 (v2.1)**: 추적성(출처 코드)으로 "개정되면 어느 문항을 고쳐야 하나"는 찾을 수 있으나, **"개정됐다는 사실 자체"는 골든셋이 스스로 알지 못한다.** 원본이 바뀌어도 아무도 안 건드리면 골든셋은 조용히 낡아 1년 뒤 틀린 잣대가 된다. → **정기 점검 주기(예: 분기)와 담당자를 사람이 정해 운영**해야 한다. 이는 규칙으로 자동화 불가한 운영 항목이다.
- **단위 묶음**: 의미를 맞게 묶었는지
- **표본 검증**: OK 통과분 중 무작위 표본을 원본과 직접 대조 (검사기 자체 점검). 표본 크기·합격 기준은 6.3을 따른다.

### 6.3 ★ 골든셋 출고 판정 — 합격/반려 기준 (v2.2 신설)

6.1 분류와 4.3 충족률을 모아 **"이 골든셋을 써도 되나"**를 가른다. 지표만 내고 끝내지 않는다(숫자만으론 사람마다 다르게 해석함).

**차단 조건 (하나라도 있으면 출고 불가 — 사람이 해소해야 함)**
- 미해결 '사람 확인' 항목이 남아 있음
- 미판정 '충돌'이 남아 있음
- 사유 없는 '누락 의심' 단위가 남아 있음

**품질 게이트 (임계값은 위험도에 맞춰 사람이 정함 — 4.3처럼 값은 비워 둠. 아래는 업계 통상 권장값)**

| 항목 | 권장 기준값 | 뜻 |
|------|-----------|----|
| 정답 근거 존재 | 100% | 모든 문항에 출처·발췌가 있어야 함 |
| 질문–정답 매핑 정확도 | 95% 이상 | 질문과 정답이 실제로 연결돼 있나 |
| 평가자 간 일치율 | 90% 이상 | 같은 문항을 누가 채점해도 같은 합격/불합격이 나오나 |
| 커버리지 충족률 | 주요 유형 80% 이상 | 4.3 식으로 계산 (고위험 업무는 95% 등 상향) |
| 표본 검수 | 통과 | 무작위 표본을 사람이 원본 대조 |

- **평가자 간 일치율(신설)**: 문항 표본을 **2명 이상**이 따로 채점해, 합격/불합격이 갈리는 비율을 본다. 많이 갈리면 → 그 문항은 *질문이 모호*하거나 *정답이 덜 정의*된 것(특히 다중 정답을 안 적어둔 경우). 고쳐서 일치율을 올린 뒤 출고.
- **표본 크기는 5개 고정이 아니라 모수에 비례**해 정하고, 통과 기준과 불합격 시 처리(전수 재점검 등)도 미리 정해 둔다.
- 위 숫자는 통상값일 뿐 법칙이 아니다 — 위험도 높은 업무면 올리고, 초기 시범이면 낮춰도 된다. 정하는 건 사람.

**판정**
- 차단 조건 0건 + 모든 게이트 통과 → **출고 가능** (골든셋 본문 확정)
- 하나라도 미달 → **반려**: 해당 항목(사람 확인·충돌·누락)을 보강·해소한 뒤 재검증
- **번외 질문은 출고를 막지 않는다** — 본문과 분리 보관하고, 필요 시 사람이 개별 승격

---

## 7. 유형 E(무응답 함정) 처리
- E형은 "자료에 없는 것"을 묻는 문항이라 **발췌가 없는 게 정상.** 1축(발췌 진위)에서 **제외.**
- 대신 "정말 자료에 그 내용이 없는가"를 원문 전체 검색으로 한 번 확인 (있는데 '없다'면 틀린 함정).

---

## 8. 검증 결과 — 표준 시트 구조

검증/추린 결과물은 다음 시트로 출력 (생성 규칙서 6장과 정합):

1. **문서 목록 (출처 인덱스)** — 문서 리스트 + 버전·날짜 + 사용여부 + 출처 코드
   - ★ **출처 코드에 버전을 포함**한다(예: `[GYE-Rev5]`). 같은 문서의 구버전·신버전이 폴더에 함께 있을 때 어느 버전에서 뽑았는지 본문만 보고도 구분되도록. (`[GYE]`만 달면 Rev4에서 뽑았는지 Rev5에서 뽑았는지 추적 불가)
   - ★ 채택된 골든셋의 출처 버전이 **문서 목록의 '사용=최신본'과 일치**하는지 대조한다. 불일치(구버전 발췌 혼입) 시 → '사람 확인'.
   - ★ 가능하면 **구버전 파일은 작업 폴더에서 분리**해, 애초에 구버전에서 발췌하는 사고를 막는다.
2. **커버리지 맵** — 의미 단위 ↔ 커버 문항. 상태는 v0.4 9종(미검토/커버됨/미커버/근거약함/자료부족/중복/충돌/사람확인/제외). 빈 단위는 사유 달린 비채움 / 누락 의심 / 표본 설계 제외(TC) / 도구 한계 제외를 구분 표기
3. **골든셋 본문** — 채택된(OK) 문항. **정답 유형(`single`/`multi_equivalent`) 컬럼 포함**, 다중이면 정답 목록·각 답 출처(3.3). ★ **`citation_id`(=커버리지 Unit ID) 컬럼**으로 각 문항이 어느 단위를 덮는지 명시(4장 조인·5.1 묶음 키). ★ 권한/거버넌스 문항(F형·RAG-03)은 단위의 **`acl_level`(14번 컬럼)을 함께 싣는다.** ※ 현재 알피스 RAG는 권한 필터 미도입(단일 공개 코퍼스)이라 acl_level은 전부 `all`·미사용 자리표시자다; **권한 도입 시** query-time ACL 채점 입력으로 활성화(그 전까지 F형은 7번 Knock-out 병행)
4. **사람 확인** — 정답 충돌·진위 실패·단위 묶음·`conflict_unresolved` 등 사람 판정 필요
5. **번외 질문** — 단독 문항 후보 (다수결 미경유, 진위는 통과)
6. **용어 구분** — 혼선 유발 용어
7. **검증 결과 보고** — 총 문항 / OK / 사람확인 / 번외 / 충돌 / 누락의심 / E형 수, 커버리지 충족률, 매핑 정확도·**평가자 간 일치율**, **출고 판정 결과(합격/반려 + 사유, 6.3 기준)**, 한계

---

## 9. 검증을 누가 하나 (도구·주체)

- **가장 정확**: 코드(스크립트)로 1축 문자 대조 + 3축 단위 대조(citation_id 결정 조인) → 사람이 결과 확인. (2축 정답 정합성은 코드로 안 되므로 3.2대로 LLM 1차 + 사람 최종)
- **모델 검증**: 여러 모델/세션에 맡길 때 — 생성한 모델과 **다른 주체**로. 원본 자료 함께 제공.
- **하지 말 것**: 골든셋을 만든 바로 그 세션에게 "네가 만든 거 검증해줘"만 하기.
  (자기가 만든 걸 자기가 봐주는 순환 — 발췌 진위·누락이 안 걸러짐)

---

## 10. 한 줄 요약

검증 = **발췌 진위(기계 대조) + 정답 정합(판단) + 커버리지 누락(단위 재추출 대조) + 여러 골든셋 비교채택(문맥·정답 정규화 다수결) + 충돌·표본(사람).**
원본 자료를 반드시 함께 줄 것. 특수문자·공백·표·말줄임·파일경계 함정에 더해, **추출 불가 문서(스캔/이미지 PDF)는 '가짜'가 아니라 '확인 불가'로 처리**해야 거짓 경보가 안 난다.
다수결은 "넣은 것"만 거르므로, 커버리지 검사로 "빠뜨린 것"을 따로 잡아야 한다.
