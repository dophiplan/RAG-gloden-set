## 1. ★ 커버리지(망라성) 체계 — v3.0 핵심

> **왜 신설했나:** 기존 방식은 "자료를 읽고 좋아 보이는 문항을 골라" 만들었다. 이건 주관적 선별이라
> 어느 조문/항목이 빠졌는지 아무도 모른다. 그 결과 "문서를 띄엄띄엄 본" 골든셋이 됐다.
> 커버리지 체계는 **문서를 빠짐없이 분해 → 각 조각이 문항으로 덮였는지 대조**해서 누락을 원천 차단한다.

### 1.1 의미 단위로 "기계적으로" 전부 쪼갠다 (생성 전)

문항을 만들기 **전에**, 문서를 "의미 단위" 목록으로 먼저 분해한다.
이 분해는 **모델의 주관 판단이 아니라 기계적 추출**로 한다(목차·번호·소제목·표 행을 빠짐없이 나열).

**의미 단위의 정의 = "하나의 질문에 답할 수 있는 최소 완결 덩어리"**

문서 유형별 단위:

| 문서 유형 | 커버리지 단위 | 추출 방법(기계적) |
|-----------|--------------|------------------|
| 규정·정책 | **조 / 항** (제N조, ①②③) | "제\d+조", 항 번호로 분할 |
| 제품 사양서 | **의미 완결된 기능 항목** | 표의 행 / 기능명 단위 |
| 매뉴얼·가이드 | **절 / 소제목** | "N.N.N 제목" 목차 단위 |
| 표(에디션·권한 매트릭스) | **의미 완결된 행(또는 행 묶음)** | 표의 행, 단 1.2 참조 |
| FAQ·헬프데스크 | **글 1건** | 문서(article) 단위 |
| **TestCase(TC)·체크리스트** | **테스트 항목 / 검증 조건 / 기대 결과** | ★전수 아님 — 층화 표본만★ (아래 주의) |
| **KnownIssue** | **이슈 / 발생 조건 / 영향 범위 / 조치** | 이슈 항목 단위 (전수) |

> ★ **TC는 전수 분해하지 않는다.** 분량이 압도적이라 커버리지맵 작업지시서 v0.4의 **층화 표본** 규칙(`TC_표본설계_{PREFIX}.md`: 기능군·우선순위·유형별 비율·표본 수)에 따라 **표본으로 뽑은 항목만** 단위화한다. 표본 설계가 미정이면 TC는 보류하고 사유를 적는다. 非TC(규정·사양서·매뉴얼·KnownIssue·FAQ)는 종전대로 전수.

### 1.2 ★ 의미가 여러 행/칸에 걸치면 "묶어서" 한 단위로 본다

기계적으로 행을 쪼개되, **의미가 여러 줄에 걸쳐 있으면 반드시 묶는다.** 끊으면 답을 못 만든다.

- 예시(끊으면 안 되는 경우): "주화자모드"(1행)와 "최대 50명"(다른 칸)이 떨어져 있으면,
  → **"주화자모드 = 최대 50명"으로 묶어야** 정답이 된다. 따로 보면 "주화자모드?"와 "50?"이 연결 안 됨.
- 일반화: 한 행으로 답이 완결되면 1행=1단위. 여러 행이 모여야 완결되면 그 묶음=1단위.
- **묶음 판단은 사람 검수 대상이다.** 생성 시 "이렇게 묶었음"을 커버리지 맵에 표시하고,
  검수자가 "더 묶어라/쪼개라"를 판단할 수 있게 한다. (자동 분해가 의미를 끊을 위험 방지)

### 1.3 커버리지 맵 작성 (생성 후) — 절차

각 의미 단위가 문항으로 덮였는지 대조표를 만든다. 절차:

1. **단위 목록 만들기**: 1.1·1.2대로 문서의 모든 의미 단위를 번호와 함께 나열.
   (예: 휴가관리지침 → 제1조, 제2조, …, 제15조, 별표1, 별표2)
2. **문항↔단위 매핑**: 각 골든셋 문항의 `citation_id`(=커버리지 Unit ID, 작업지시서 v0.4)로 어느 단위를 덮었는지 **결정 조인**한다. (출처 코드는 사람용 표기로 병기 가능하나, 기계 매핑 키는 citation_id)
   (판정 기준: 문항의 citation_id가 그 단위 Unit ID와 일치하면 "커버됨")
3. **빈 단위 식별**: 어떤 문항도 덮지 않은 단위를 찾아낸다.
4. **빈 단위 분류 (1.4)**: 각 빈 단위에 상태값과 사유를 단다.

> ★ **이 맵은 두 층이다 (작업지시서 v0.4와 정합):**
> - **인벤토리(정본)** = 작업지시서 Layer 1. 단위마다 Unit ID·type·acl_level·source_location·related_units·tags·citation_id 등 메타데이터를 보유. 커버리지맵 작성의 **출발점이자 단일 진실원천**.
> - **매핑 뷰(파생)** = 아래 `단위↔커버 문항↔상태` 표. 손으로 유지하지 말고 **citation_id 조인으로 파생 계산**한다(골든셋이 커질 때 stale 방지). 아래 형식은 그 파생 뷰의 예시일 뿐, 메타데이터 전체는 인벤토리에 있다.

**커버리지 맵(매핑 뷰) 형식 (시트로 출력):**

| Unit ID | 단위 내용(요약) | 커버 문항(citation_id 조인) | 상태 |
|---------|---------------|------------------------------|------|
| HR-REG-005 | 연차휴가 부여 | HR-001, HR-002 | 커버됨 |
| HR-REG-006 | 연차휴가 산정 | (없음) | **미커버** |
| HR-REG-별표1 | 가산 연차 일수표 | HR-002 | 커버됨 |

### 1.4 다 잡되, 안 만든 것은 상태값으로 표시한다 (버리지 않음)

- **모든 의미 단위를 커버리지 맵에 올린다.** "제외 경계"를 미리 두지 않는다(목적·정의·부칙도 다 올림).
- 문항을 만들지 **않은** 단위는 삭제하지 말고 **상태값**으로 남긴다(= 미사용이지 누락 아님). 사유에 따라:
  - `미커버` — 문서엔 있으나 아직 질문/골든셋으로 미전환 (시험 가치는 있음)
  - `자료부족` — 원천자료 부족으로 정확한 답 구성 곤란
  - `근거약함` — 답은 가능하나 원문 근거가 짧거나 불명확
  - (기존 단일 용어 `보류`는 폐기 — 위 셋 중 사유에 맞게 적는다)
- 빈 단위에 사유·상태가 없으면(상태 `미검토`로 방치) 그건 실수 누락이다 → 채워라.
- **이렇게 하면 "실수 누락(미검토 방치)"과 "의도적 비채움(사유 달린 미커버/자료부족/근거약함)"이 구분된다.**

### 1.5 커버리지의 한계 (정직하게 명시)

- 커버리지는 "문서 안의 단위"를 다 덮는 것이다. **문서에 없는 것**(실제 사용자가 묻지만 규정엔 없는 것)은
  커버리지로 못 잡는다. 그건 사용자 질문 로그가 있어야 한다(3.4 참조).
- 단위를 "묶는" 판단이 틀리면(과도하게 묶거나 쪼개면) 커버리지도 부정확하다 → 1.2 사람 검수 필수.

## 2. 발췌 3원칙 (0장 2번의 상세)

정답의 근거가 되는 문장을 자료에서 **글자 그대로** 복사해 '근거 원문 발췌' 칸에 넣는다.

- **(a) 발췌 칸에 설명·주석을 섞지 마라.** "(4번째 열=visual)", "사양서:", "(구분: Spec)" 같은
  본인 주석 금지. 원문 문장만. (주석이 섞이면 자동 문자대조가 헛걸림)
- **(b) 말줄임(…) 자제.** 중간 생략 말고 연속된 한 문장을 그대로. 길면 핵심 한 문장만 통째로.
- **(c) 표(○ - 기호) 기반 정답**은 해당 행을 기호까지 그대로 복사하고, 어느 열이 어느 에디션인지는
  발췌가 아니라 '정답' 칸에 적는다.

### 2.1 ★ 조합(멀티홉·복합·표) 문항의 발췌 예외 (v3.0 신설)

멀티홉·복합 문항은 **여러 곳의 발췌를 조합**하므로 "한 문장이 글자 그대로"가 성립하지 않는다.
이 경우:

- 발췌를 **단위별로 여러 개** 넣는다. 각 발췌는 각자의 출처에서 글자 그대로.
- 예(멀티홉): 발췌1 `[A]제5조 "..."` + 발췌2 `[B]별표1 "..."` 를 구분해서 나란히.
- 정답 칸에는 "발췌1과 발췌2를 어떻게 연결해 답이 나오는지"를 적는다.
- 표 기반도 동일: 흩어진 셀(행 라벨 + 값)을 각각 발췌로.

## 3. 문항 구성과 유형

### 3.1 문항 1개의 구성 — 15개 항목 (엑셀 컬럼 순서 고정)

| # | 항목 | 설명 |
|---|------|------|
| 1 | ID | 유형 접두어+번호. 예: HR-001(A형), HR-E01(E형) |
| 2 | 유형 | 3.2의 유형 중 하나 |
| 3 | 출제 의도 | 검증 능력 1가지 + **RAG 기법 코드**(5장 RAG-01~11) 괄호 명시 |
| 4 | 질문 | 사용자가 실제 입력할 자연어. 구어체·오타 변형 가능 |
| 5 | 정답 (필수 포함 요소) | 정답 핵심 + 필수 포함 요소(수치·절차 순서 등). **여러 답이 다 맞으면 15번 `answer_type=multi_equivalent`로 표시하고 정답 칸에 ①② 형식으로 나열한다(3.6). 정답은 필수 요소만 — 발췌 요약·전사 금지, 150자 이내 권장(§3.7).** |
| 6 | **근거 출처 (citation_id + 출처 코드)** | **형식: `citation_id들 ; 사람용 출처 코드들`** — 세미콜론(`;`) 1개로 좌(기계 조인 키)·우(사람용) 분리, 같은 쪽 다중은 `+`. 좌측 = `citation_id`(=커버리지 Unit ID, 작업지시서 v0.4). 단일 예: `RC-HELP-SEC-001 ; [HYU-Rev5]제5조①`. 조합 예: `RC-SPEC-FUNC-014 + RC-MANUAL-ADMIN-007 ; [HYU-Rev5]제5조 + [GYE-Rev5]별표1`. citation_id 미부여 시 좌측을 비움(`; [HYU-Rev5]제5조`) → 검증이 source 키 보조 매칭/누락 플래그 (정식 규격은 4장 박스) |
| 7 | 합격 기준 | 4.1 기본값 + 필수요소 + **Knock-out 조항**(치명적 감점). 예: 필수: macOS 미지원 명시, 타 OS 혼동 시 0점 |
| 8 | 난이도 | 하/중/상 |
| 9 | 기대 라우팅 | 문서검색 / DB통계(NL2SQL) / 하위질의분할(Sub-Query) / 거절(E형) |
| 10 | 검증 상태 | 항상 `초안` (validate_goldenset 허용값: `초안`/`검토중`/`검증완료` 중 하나. "검수 대기" 뉘앙스는 11번에) |
| 11 | 작성자/검증자 | "(모델명) 초안 / (사람) 검수" |
| 12 | **근거 원문 발췌** | 6번 위치 원문 문장 그대로. 조합 문항은 2.1대로 여러 개 |
| 13 | 신뢰도 | 출처 2개+ 일치=높음 / 단일=보통 |
| 14 | acl_level | 접근 권한 등급 = 회사/본부/팀/파트/개인/공개. 그 단위의 `acl_level` 복사. **현재는 권한 필터 미도입 → 전부 `all`**(맨 끝 선택 컬럼, 미래 대비) |
| 15 | **answer_type** ★v3.3 | `single`(정답이 하나) / `multi_equivalent`(여러 답이 모두 정답 — 3.6). 비면 single로 간주. 검증 규칙서 v2.4·judge 표준의 판정 분기 키 |

> ★ **6번 컬럼 = 커버리지맵과의 조인 키 (v3.2).** 기존엔 "출처 코드"만 적었으나, 커버리지맵 작업지시서 v0.4의 join을 살리려면 **`citation_id`(커버리지 Unit ID)를 기계 키로 적고** 사람용 출처 코드는 병기한다. 검증 규칙서 v2.4 §4.1·§5.1이 이 citation_id로 단위↔문항을 결정 조인한다. (컬럼을 새로 추가하지 않고 6번 안에 담아 loader 헤더는 13컬럼 그대로 유지). **6번 칸 내부 형식(`;`로 좌우 분리, 다중 `+`)은 4장 "6번 칸 형식 규격" 박스를 따른다.**

> ★ **acl_level (v3.2 → 14번 정식 컬럼).** 접근 권한 등급(회사/본부/팀/파트/개인/공개)을 단위에서 문항으로 복사한다. **14번을 맨 끝 선택 컬럼으로 두면 loader가 발췌·신뢰도와 동일하게 "헤더 이름으로 찾아 읽는" 방식이라 1~10번 위치검증을 안 건드려 깨지지 않고, `config.yaml`은 컬럼 정의가 없어 무수정이다**(코드 확인 결과 — 런북 함정 2는 1~10번 고정 컬럼에만 해당). ⚠️ **현재 알피스 RAG는 권한 필터 미도입(단일 공개 코퍼스)이라 acl_level은 전부 `all`이고 어떤 채점에도 쓰이지 않는 미래 대비 자리표시자다.** 권한 도입 시 query-time ACL 채점 입력으로 활성화한다(그 전까지 F형은 7번 Knock-out "권한 등급 위반 시 0점"을 병행).

### 3.2 문항 유형

| 유형 | 이름 | 설명 |
|------|------|------|
| A | 단순 문서 조회 | 자료에 답이 그대로 있는 질문 |
| B | 통계/수치 집계 | 개수·평균·비교 (route=DB통계) |
| C | 복합 질문 | 한 문장에 2개+ 독립 질문 (route=하위질의분할) |
| D | 멀티홉 | 단서가 연쇄로 이어져야 답 (A→B→정답) |
| E | 무응답 함정 | 자료 **어디에도 해당 정보가 존재하지 않는** 질문. 정답="자료에 없음" 명시, 지어내면 0점. **발췌 칸은 반드시 공란.** ★원문에 "미지원/X/제한"이 **명시**된 것은 E가 아니라 근거 있는 사실(A/G형)이다 — 명시된 미지원을 E로 분류 금지(v3.3). ★부재의 기준은 **정본 문서**다(코퍼스 아님) — 실물 RAG 코퍼스 export가 있으면 정본+코퍼스 **이중 부재 확인**(코퍼스 대조=1차 필터, 최종 판정=2축). 코퍼스에만 없는 내용은 E형 출제 금지 → 인입 누락 리포트로(v3.4) |
| F | 권한/거버넌스 | 특정 권한·역할의 가능/불가 (권한 밖 정보 새면 0점) |
| G | 경계/예외 | 버전·OS·에디션별 다른 동작의 경계 |

### 3.3 ★ 유형·난이도 분포 강제 (v3.0 신설 — 단순 조회 편중 방지)

> **왜 신설했나:** 기존 골든셋은 대부분 A형(단순 사실 조회: "연차 15일")이었다.
> 그러나 실제 사용자는 "연차 어떻게 써요?" 같은 복합·종합 질문을 더 많이 한다.
> A형만 많으면 "쉬운 시험만 잘 보는" 착시가 생긴다.

**구체 기준 (모호한 "적절히" 금지, 숫자로):**
- **A형(단순 조회)은 한 배치의 60%를 넘지 않는다.** (30문항 기준 A형 최대 18개)
- 자료에 소재가 있으면 **반드시** 다음을 포함:
  - C형(복합) 또는 D형(멀티홉): 합쳐 **최소 3개** (연쇄·복합 소재가 있을 때)
  - RAG-06(추상 요구) 유형: 최소 1~2개 (선언적 질문 매칭 가능 시)
- **"정답이 한 줄로 안 떨어지는" 실전형 질문**(절차·종합)을 의도적으로 포함한다.
- 난이도 배분 권장: 하 40% / 중 40% / 상 20%

**단, 억지 금지 (기존 원칙 유지):** 자료에 연쇄 단서·복합 조건이 **실제로 있을 때만** C·D형을 만든다.
없는데 억지로 멀티홉을 지어내지 않는다. 소재가 없어 비율을 못 채우면 작업 보고에 "소재 부족"이라 적는다.

### 3.4 ★ 유형 분포의 한계 (정직하게 명시)

- 3.3은 "자료 안에서 만들 수 있는 복합 문항"까지만 강제한다.
- **"실제 사용자가 무엇을, 어떻게 묻는지"는 자료에 없는 정보다.** 진짜 실전 질문 패턴은
  사용자 질문 로그(고객센터 문의, 사내 실제 질문 등)가 있어야 나온다.
- 그런 로그가 없으면 이 부분은 비어 있음을 인정하고, 작업 보고에 "사용자 질문 로그 미확보 — 실전 패턴 보강 불가"로 명시한다.

### 3.5 출제 의도를 먼저 정하는 법 (질문 창작 금지)

질문을 먼저 지어내지 말 것. 순서:
1. **1장 커버리지대로 의미 단위를 먼저 다 나열** (이게 출발점)
2. 각 단위에서 "테스트할 능력"을 뽑고 유형(3.2) 배정
3. 단위마다 질문을 1~N개 생성 (단위에 든 사실 수만큼 자연스럽게 — 수치 10개면 ~10문항, 정의 1개면 1문항)
4. 정답·출처 코드·발췌를 자료에서 채움
5. **커버리지 맵으로 빈 단위 점검** → 상태값·사유 기재 (1.3~1.4: 미커버/자료부족/근거약함)

### 3.6 ★ 다중 정답 처리 (v3.1 신설 — RAG 통합 시스템 필수)

실제 RAG 시스템에선 정답이 하나가 아닐 때가 있다. "휴가 신청 어떻게?"는 *그룹웨어로도, 인사시스템으로도* 다 맞는다. 정답을 하나만 적으면, 다른 맞는 답을 한 시스템을 **틀렸다고 잘못 채점**한다. 그래서 정답 유형을 구분해 만든다.

| 정답 유형 | 뜻 | 처리 |
|-----------|----|------|
| **single** | 정답이 사실상 하나 (예: 연차 = 15일) | 5번 칸에 정답 하나 |
| **multi** | 여러 답이 **모두 똑같이 맞음** (예: 신청 경로 2가지) | 15번 `answer_type=multi_equivalent` + 5번 칸에 ①② 나열 (아래) |
| **충돌(conflict)** | 하나만 맞는데 **아직 안 가림** (예: A=15일, B=20일) | multi 아님. **0장 3번대로 "충돌"로 분리** |

**표기 형식 (v3.3 — `answer_type` 컬럼 방식):**
- 15번 `answer_type` = `multi_equivalent`
- 5번 정답 칸: `① 그룹웨어 접속 후 신청 ② 인사시스템 휴가 메뉴 이용 / 필수: ①② 중 하나의 절차를 정확히, 모두 빗나가면 0점`
- (구 `[다중정답]` 대괄호 태그는 v3.3에서 폐지 — 태그와 컬럼이 이원화되어 검증 라인과 어긋났던 문제 해소)

> **★★ 가장 중요한 가드 — "다중 정답"과 "충돌"을 절대 섞지 마라.**
> 다중 정답은 *둘 다 맞는 것*, 충돌은 *하나만 맞는데 안 가린 것*이다.
> 충돌을 "정답 둘 다"로 넣으면 **틀린 답을 한 시스템도 합격**해 채점표가 망가진다(정답 부풀리기 사고).
> "둘 다 진짜 맞나?"에 확신이 없으면 multi가 아니라 충돌이다.

- **나열하는 각 답은 발췌 3원칙(2장)대로 자료에 근거가 있어야 한다.** 근거 없는 답을 목록에 넣지 말 것.
- 각 답의 출처가 다르면 6번(출처 코드)·12번(발췌)에 각각 표기한다(2.1 조합 발췌와 동일 방식).
- **채점 연동:** 검증 규칙서 v2.4 §3.3 및 judge 프롬프트와 일치한다 — multi는 "목록 중 **하나와** 의미상 일치하면 정답"으로 채점된다(전부 말할 필요 없음).

### 3.7 ★ 문항 품질 3규칙 (v3.3 신설 — RC 1,242문항 실측 사고 기반)

**① 질문 유일성 (중복 질문 332건 사고):**
질문 텍스트만 읽고 **어느 단위(사실)를 묻는지 특정**돼야 한다. 동일 질문 텍스트 중복 금지. 섹션명(예: "OS 지원 기능은…")이 아니라 그 단위의 **실제 기능명·OS/브라우저·플랫폼·버전 조건**을 질문에 넣는다.
- ❌ "지원 정책 기능은 어떤 플랫폼·조건에서 지원되나요?" (24개 단위가 같은 질문)
- ⭕ "안전모드로 재접속은 Mac→Win 환경에서 지원되나요?"

**② 원천 빈 값 (빈 값 정답 20건 사고):**
원천 셀이 비어 있으면 그 값을 정답에 넣지 않는다("최소지원: ," ❌). 해당 문항은 만들지 말고 커버리지맵 상태를 `사람확인`으로 두거나, 빈 값 없이 성립하는 문항으로 재설계한다.

**③ 정답 형식 (요약형 정답 506건 사고):**
정답은 **필수 포함 요소만** — 발췌를 요약·전사하지 않는다. 150자 이내 권장. 정답이 길어지면 채점(2축)의 변별이 흐려진다.

## 4. 추적성 — 출처 코드 (v3.0 신설)

> **왜 신설했나:** 규정은 개정된다. "이 문항이 어느 문서에서 왔나"를 알아야 그 문서가 바뀌었을 때
> 고칠 문항을 즉시 찾는다. 골든셋을 "한 번 만들고 끝"이 아닌 "유지보수되는 자산"으로 만든다.

- **모든 문항의 '근거 출처' 칸(6번)에 출처 코드를 단다.** 출처 코드는 "문서 목록 시트"의 약칭과 연결.
  - 예: 휴가관리지침=`[HYU]`, 경조사규정=`[GYE]` → 문항 출처 `[HYU] 제5조①`
- **조합 문항은 엮은 문서를 전부 표기.** 예: `[HYU]제5조 + [GYE]별표1`
- 문서 약칭(출처 코드) 정의는 "문서 목록 시트"(6장)에 둔다.
- 효과: 문서 개정 시 → 목록에서 약칭 찾기 → 본문에서 그 약칭 필터 → 해당 문항만 재검토.

> ★ **두 개의 키를 구분 (v3.2):** 6번 칸엔 성격이 다른 두 키가 함께 산다.
> - **`citation_id`(=커버리지 Unit ID, 예 `RC-HELP-SEC-001`)** = 커버리지맵↔골든셋을 잇는 **기계 조인 키**. 검증 규칙서 §4.1·5.1이 이걸로 단위 동일성을 결정 판단.
> - **출처 코드(예 `[HYU-Rev5]제5조`)** = 사람이 읽는 **개정 추적용 라벨**(문서·버전·조항). 검증 규칙서 §8대로 버전을 포함(`[GYE-Rev5]`).
> 둘은 대체 관계가 아니라 병기한다. citation_id는 "어느 단위냐"(기계), 출처 코드는 "어느 문서·버전·조항이냐"(사람·개정 추적).

> ★ **6번 칸 형식 규격 (v3.2 — 파서가 두 키를 가르는 규칙, 이것이 정본):**
> ```
> citation_id들  ;  사람용 출처 코드들
> ```
> - **세미콜론(`;`) 1개**로 좌(기계 조인 키)·우(사람 출처 코드)를 가른다. 하이픈(`-`)은 ID 안에 이미 쓰여(`RC-HELP-SEC`) 구분자로 못 쓰므로 `;`로 고정.
> - **같은 쪽에 여러 개면 `+`로 잇는다**(조합 문항). 파서: 6번 칸을 `;`로 잘라 **왼쪽**을 취하고 그 안을 `+`로 split → citation_id 리스트.
> - **citation_id가 아직 없으면 좌측을 비우고 `; 출처코드`만** 적는다 → 검증 §4.1이 source 키로 보조 매칭하거나 '근거 연결 누락'으로 플래그.
> - 검증 규칙서 v2.4 §4.1·§5.1이 이 규격대로 6번 칸을 파싱해 결정 조인한다. SOP §2.1·생성 §3.1이 이 규격을 참조.

## 5. RAG 기능별 검증 커버리지 (RAG-01 ~ 11)

골든셋은 단순 사실 조회만이 아니라 RAG 각 기능이 작동하는지 고르게 검증해야 한다.
아래 11기법을 유형에 분배하고 '출제 의도'에 코드를 명시한다. (특정 벤더 전용 아닌 보편 기법)

| 코드 | 기법 | 출제 방법 | Knock-out | 박스 |
|------|------|----------|-----------|------|
| RAG-01 | 계층 결합 (Parent-Child) | 표·분류에서 세부 수치/기능명 | 자식만 보고 부모 문맥(에디션) 놓치면 0점 | 6 |
| RAG-02 | 전후 문맥 (Sentence Window) | 대명사·지시어로 앞뒤 없이는 모를 질문 | 지칭 대상 못 하면 0점 | 6 |
| RAG-03 | 권한 필터링 (Metadata) | 부서·보안등급 제한 조건 | 권한 밖 내용 섞이면 0점(게이트) | **2** |
| RAG-04 | 유의어·구어체 | 정형 용어를 은어·약어로 | 정형 문서 못 찾으면 실패 | 6 |
| RAG-05 | 다중 조건 복합 (Sub-Query) | 한 문장에 다른 문서 2질문 | 한쪽 누락하면 0점 | 5 |
| RAG-06 | 추상 요구 (HyDE) | 매칭 문장 없는 선언적 질문 | 핵심 단락 못 찾고 일반론만 답하면 실패 | 6 |
| RAG-07 | 고유명사·코드·오타 | 모델명·에러코드를 오타/한글발음 | 유사 다른 항목 답하면 0점 | 6 |
| RAG-08 | 멀티홉 (Multi-hop) | 연쇄 단서 (A→B→정답) | 중간 건너뛰고 추측하면 0점 | 5·6 |
| RAG-09 | 유사 노이즈 (Reranking) | 버전·OS별 제목 비슷·내용 다른 낚시 | 틀린 버전/OS로 답하면 0점 | 6 |
| RAG-10 | 롱컨텍스트 (Compression) | 긴 문서 통째 상황 | 무관 내용으로 흐려지거나 환각 시 실패 | 6 |
| RAG-11 | 통계 집계 (NL2SQL) | 개수·평균·다중 비교 | 어림수 내면 0점, Exact Match | 5·6 |

### 5.1 PASS 처리 규약 — 재료가 없으면 건너뛴다

각 규칙엔 "적용 전제조건"이 있다. 해당 데이터가 자료에 없으면 **PASS(해당 없음)**로 처리하고
억지로 만들지 않는다. PASS는 "자료가 생기면 자동 활성화"되는 대기 상태다.

- 표시법: ID=PASS-RAG-03, 유형=PASS(전제조건 미충족), 사유="이 자료엔 권한별 문서 세트 없음"
- PASS 행은 집계 제외하되 커버리지 맵에 "활성화 대기"로 기록.

(전제조건 표는 부록 B. 자료 유형마다 PASS/적용이 달라짐)

## 6. 출력 형식 — 표준 시트 구조

엑셀 1개에 시트 (순서 고정):

1. **문서 목록 (출처 인덱스)** ★ — 첫 시트 필수
   - 파악한 모든 문서 리스트 + 버전·날짜 + 사용여부(사용/보류/제외) + **출처 코드(약칭)**
   - 최신본 판단 근거(시행일·파일날짜) 기재. 판단 안 되면 "사람 확인"으로.
2. **커버리지 맵** ★ — 의미 단위 ↔ 커버 문항 대조 (1.3 형식, citation_id 조인 파생 뷰). 빈 단위는 v0.4 9종 상태값(미커버/자료부족/근거약함 등)·사유 포함.
3. **골든셋 본문** — 문항들, 3.1의 13개 컬럼.
4. **충돌 목록** — 자료끼리 다른 항목 (주제 / A주장 / B주장 / 영향 문항 / 판정 필요).
5. **용어 구분** — 혼선 유발 용어 사전 (혼동 방지).
6. **작업 보고** — 생성 수, 유형 분포(3.3 충족 여부), 커버리지 충족률, 충돌 수, 사람 판정 필요 항목, 한계(3.4 등).

## 7. 좋은 문항의 조건 (체크리스트)

- [ ] 질문 안에 정답이 들어있지 않다
- [ ] 출처 코드로 어느 문서·어느 단위에서 왔는지 특정된다 (조합이면 전부)
- [ ] 근거 원문 발췌가 실제 자료 문장과 **글자 그대로** 일치한다 (조합은 단위별 발췌)
- [ ] 단순형은 한 가지만 테스트한다 / 복합·멀티홉형은 단계가 명시돼 있다
- [ ] 숫자(용량·일수·금액·버전)는 자료의 표/문장에서 정확히 가져왔다 (표는 열 헷갈림 주의)
- [ ] 실제 사용자가 물을 법한 표현이다
- [ ] 다중 정답이면 나열한 답이 모두 자료에 근거가 있고, "충돌(하나만 맞음)"을 다중으로 위장하지 않았다 (3.6)

## 9. 이 규칙서가 못 하는 것 (정직한 한계)

- **실제 사용자 질문 패턴**: 자료 밖이라 못 만든다. 질문 로그 확보 시 보강. (3.4)
- **버전 최신성 판단**: 문서 시행일·파일날짜로 추정하되, 확정은 사람만 가능(개정 시행 여부 등). 애매하면 사람 확인.
- **의미 단위 묶음의 정확성**: 자동 분해가 의미를 끊을 수 있어 사람 검수 필요. (1.2)
- **모델 공통 누락**: 여러 모델을 돌려도 다 같은 단위를 놓칠 수 있다 → 커버리지 맵(기계적 대조)으로만 잡힌다.
  그래서 1장 커버리지는 모델 판단이 아닌 기계적 추출이어야 한다.
