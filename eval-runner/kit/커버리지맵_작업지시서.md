# 커버리지맵 작업지시서 — OKF식 2층 분해 (공통 마스터) v0.5

> **v0.4 → v0.5 변경 요약 (DECISIONS DEC-020·021 반영, 2026-07-08)**
> 1. **cross-batch 앵커 무결성 (DEC-020)**: `related_units`의 `영역ID:절명` 앵커에서 영역ID는 **대표 단위가 실존하는 배치의 실제 접두**여야 한다. 실존하지 않는 영역명 금지. 통합 단계에서 앵커 전량 실ID 해석(미해석 0)을 통과해야 하며, 복합 절명(단위 2개 이상에 걸침)은 앵커를 분리한다.
> 2. **제외/폴딩 식별과 대장 (DEC-021)**: 제외·폴딩 단위 식별의 1차 기준은 **상태값**(제외/중복)이다. 대장류 시트(제외대장·폴딩대장·근거약함)는 상태값 기준으로만 구성한다(접두 기준 혼용 금지). 검수는 대장-본체 집합 일치(차집합 0)로 판정. ID 접두(`RC-EXCLUDED-*`)는 트랙 간 통일하되, 통합 도구의 필터 기준은 상태 필드로 한다.
>
> **v0.3 → v0.4 변경 요약**
> 1. **`related_units` 영속성 앵커 추가**: related_units가 bare Unit ID만 저장하던 모순 해소. Unit ID는 재분해 시 밀리는 표면 ID(6장)이므로, 영속 연결은 source 키 기준으로 재유도하도록 규칙 명시. (6장 KI 매핑 영속성 원칙과 통일)
> 2. **dedup 발화 시점 명시**: source 키를 단위마다 유일하게 만든 결과(2.1), 한 작업자·한 패스 내에서는 dedup이 발화하지 않음. dedup은 **다중 작업자/모델 union 병합 시에만** 작동함을 7장에 명시.
> 3. **필수/선택 컬럼 표시**: Layer 1 메타데이터(3장)에 `필수/선택/파생` 구분 추가. 비개발자 작업 부하 경감.
>
> **v0.2 → v0.3 변경 요약 (유지)**
> 1. **source 키 유일성 규칙 신설**: "단위 쪼개기(2.1)"와 "source 키 dedup(7장)"의 충돌 해소. `(source/resource + source_location)`은 단위마다 유일해야 하며, `source_location`은 단위를 유일 식별하는 입도까지 적는다.
> 2. **provenance 필드 추가**: `extracted_by`(생성자/모델), `confidence`(상/중/하) 신설. 다중 작업자/다중 모델 union·dedup·충돌 tie-break, 검수 우선순위, 상태값 보조 힌트에 사용. ※ 커버리지맵 `confidence`(추출 충실도)는 골든셋 `confidence`(답변·문항 타당도)와 **측정 대상이 다르다** — 산술로 합치지 않고 표기 관례만 맞춘다.
> 3. **`related_units` 컬럼 신설(Layer 1)**: 그룹 간 연결(cross-group join)을 Layer 1 메타데이터로 박아 안정화. (예: TC↔Spec, KnownIssue↔Manual)
> 4. **TC 층화 표본 파라미터 포인터 명시**: 댕글링 레퍼런스 제거. 파라미터의 소재(별도 문서/섹션)를 명시하고 미정 시 보류 규칙 재확인.
> 5. **KnownIssue ID 확정**: 단위는 `{PREFIX}-KI-###` 신규 발급(A안), 기존 `RC-K01~22`는 Question ID로 유지. 매핑은 RC-KI 번호 + **source 키**를 함께 기록해 재분해 시에도 재유도 가능하게 함.
> 6. **카디널리티 명시**: "답변 가능한 질문"은 단위→질문 1:N(대표 후보 1개 기록, 실제 확장은 골든셋), `커버됨/미커버`는 citation_id join 파생값 권장.
>
> **v0.1 → v0.2 변경 요약 (유지)**
> 1. **입자 분리**: "커버리지 단위(고운 입자, 표의 행)"와 "OKF 지식 개념=Concept(거친 입자, .md 파일)"을 명확히 2층으로 분리. v0.1이 둘을 한 단어로 섞은 문제 해결.
> 2. **TC 예외 명시**: TC는 전수 분해가 아니라 층화 표본(stratified sampling) 별도 적용.
> 3. **중복/충돌 판정 기준 신설**: dedup은 질문 텍스트가 아니라 source 키 기준.
> 4. **거버넌스(ACL) 필드 추가**: `acl_level` 신설. `user_type`은 "독자 역할"이지 "접근 권한"이 아님을 명시.
> 5. **ID 정합성**: KnownIssue ID 스킴 통일, 단위 ID / 질문 ID / OKF Concept ID 3개 네임스페이스 정리.
> 6. **citation_id 정의 명확화**: 자기 참조 중복이 아니라 "골든셋이 근거를 지목하는 조인 키"임을 명시.
> 7. **공통화**: 맨 위 제품 설정 블록만 교체하면 RC/RV/RM 등 어느 제품에도 적용.

## 0. 이 문서의 목적과 2층 구조 (가장 먼저 이해할 것)

이 문서는 RAG 구축을 위한 **커버리지맵 생성 작업자용 공통 지시서**다.
목표는 원천 문서를 빠짐없이 의미 단위로 분해하고, 각 단위에 RAG·골든셋·거버넌스에 필요한 메타데이터를 부여하는 것이다.

**핵심: 산출물은 입자 크기가 다른 2개의 층(layer)이다. 섞지 않는다.**

| 층 | 이름 | 입자 | 형태 | 생성 시점 | 단위 = 무엇 |
|---|---|---|---|---|---|
| **Layer 1 (필수)** | 커버리지맵 | **고운 입자** | 표(Excel/XLSX) | 항상 | "질문 하나로 답하는 최소 의미 단위" = **표의 행 1줄** |
| **Layer 2 (선택)** | OKF 번들 | **거친 입자** | `.md` 파일 디렉토리 | 위키/지식베이스로 서빙할 때만 | "도메인 엔티티 하나"(기능·문서·런북) = **파일 1개** |

> **왜 분리하나:** OKF에서 `concept`은 "파일 1개 = 엔티티 1개"(거친 입자)다. 우리 골든셋 작업의 "질문 단위"(고운 입자)와 입자 크기가 다르다. 둘을 1:1로 등치시키면 사실 하나당 .md 파일 하나가 생겨 수천 개 파일로 폭발하고, OKF가 의도한 "엔티티 단위 위키"와 정반대가 된다.
> **올바른 매핑:** 커버리지맵의 **행 여러 개 → OKF 파일 1개**. 각 행은 그 파일 *안의 섹션(헤딩)*으로 들어간다. (예: 행 5개 "2단계 인증 설정/조건/예외/오류/제한" → `security/two-factor-auth.md` 1개 파일의 5개 헤딩)

Layer 1만 만들어도 골든셋·RAG 평가는 완결된다. Layer 2는 본부장님이 OKF 위키로 서빙하라고 명시할 때만 추가 생성한다.

## 0.5 제품 설정 블록 (이 블록만 교체하면 제품 공통)

작업 시작 전 아래 값을 해당 제품에 맞게 채운다. 본문은 이 변수만 참조한다.

```yaml
PRODUCT:        RemoteCall          # RemoteCall | RemoteView | RemoteMeeting | ...
PREFIX:         RC                  # RC | RV | RM
SOURCE_ROOT:    RC_RAG_AI_file/     # 원천 자료 루트 경로
HELPDESK_BASE:  https://help.remotecall.com/hc/ko/
ACL_DEFAULT:    회사                 # 출처에 별도 표시 없을 때 기본 접근등급
```

> 예: RemoteMeeting이면 `PRODUCT=RemoteMeeting / PREFIX=RM / SOURCE_ROOT=RM_RAG_AI_file/` 로만 바꾸면 동일 절차 적용.

## 1. 사용할 원천 자료

### 1.1 우선 사용 대상
- `{SOURCE_ROOT}사양서/`
- `{SOURCE_ROOT}매뉴얼/`
- `{SOURCE_ROOT}TC/`
- `{SOURCE_ROOT}KnownIssue/`
- 사용자가 제공한 `{PRODUCT}` Helpdesk URL 목록 (`{HELPDESK_BASE}…`)

### 1.2 사용하지 않는 대상
- 구버전 사양서 / 최신본과 중복되는 PDF·XLSX
- 기존 골든셋 산출물 / 기존 평가 결과물
- `.DS_Store`, `__MACOSX`, `._파일명` 등 시스템 파일
- `{PRODUCT}`이(가) 아닌 타제품 자료
- 예시·레거시 용도 시트

제외 사유는 필요 시 `비고`에 기록한다. (버전 판단 규칙: **2026에 가장 가까운 날짜 = 최신본**)

## 2. 핵심 원칙

### 2.1 커버리지 단위(Coverage Unit) 정의 — Layer 1, 고운 입자

`커버리지 단위`는 **질문 하나로 답할 수 있는 최소 의미 단위**이며, **커버리지맵 표의 행 1줄**에 대응한다.

해당 예: 기능 하나 · 조건 하나 · 절차 한 단계 · 예외 케이스 하나 · 표의 행 하나 · FAQ 질문 하나 · Helpdesk 답변 항목 하나.

한 단위 안에 사실이 여러 개면 반드시 쪼갠다. (단위 크게 묶기 금지)

> **★ source 키 유일성 (v0.3):** 단위를 쪼개면(2.1) 같은 출처 위치에서 단위가 여러 개 나올 수 있다. 그런데 dedup 키는 `source/resource + source_location`(7장)이므로, `source_location`을 `p.12`처럼 거칠게 적으면 쪼갠 단위들이 같은 키를 갖게 되어 dedup이 도로 합쳐버린다(쪼개기 ↔ 합치기 충돌). 따라서 **`source_location`은 단위가 유일하게 식별되는 입도까지 적어, `(source/resource + source_location)`이 단위마다 유일하도록 한다.** 예: `p.12` ❌ → `p.12 / 표2 / 3행` ⭕, `시트명!A23` ⭕, `본문 2단계 / 예외 항목 b` ⭕.

### 2.2 OKF 지식 개념(Concept) 정의 — Layer 2, 거친 입자 (선택)

`OKF Concept`은 **도메인 엔티티 하나 = .md 파일 하나**다. (기능 페이지·문서·런북·API 등)
커버리지 단위 여러 개가 하나의 Concept 파일로 묶이며, 각 단위는 파일 내부 헤딩이 된다.
**이 층은 OKF 번들을 실제로 생성할 때만 만든다. 8장 참조.**

### 2.3 문서 유형별 분해 기준

| 문서 유형 | 분해 기준 | 전수/표본 |
|---|---|---|
| 규정/정책 | 조, 항, 호 단위 | 전수 |
| 사양서 | 표의 행, 기능, 조건 단위 | 전수 |
| 매뉴얼 | 절, 소제목, 절차 단계 단위 | 전수 |
| **TC/Check List** | 테스트 항목, 검증 조건, 기대 결과 단위 | **표본(층화 표본) — 아래 예외 적용** |
| KnownIssue | 이슈, 발생 조건, 영향 범위, 조치 단위 | 전수 |
| FAQ/Helpdesk | 질문 항목·답변 항목 단위 | 전수 |

> **★ TC 예외 (v0.2 신설):** TC는 분량이 압도적이라 **전수 분해하지 않는다.** 별도 정의한 **층화 표본(stratified sampling) 파라미터**(기능군·우선순위·유형별 비율)에 따라 표본만 단위화한다. 非TC 원천은 원문 대비 **1:1 근접 전수**를 목표로 한다. TC 표본 파라미터가 아직 미확정이면 그 사실을 `비고`에 남기고 표본 작업을 보류한다.
>
> **★ TC 표본 파라미터 소재 (v0.3):** 위 파라미터는 본 지시서에 인라인하지 않고 **별도 문서 `TC_표본설계_{PREFIX}.md`(또는 프로젝트_문서/ 내 해당 섹션)** 에 둔다. 작업자는 작업 시작 전 그 문서의 (a) 기능군 분류, (b) 우선순위 등급, (c) 유형별(정상/예외/경계) 목표 비율, (d) 그룹별 표본 수를 확인한다. **현재 코퍼스 확정 대기 중이면 파라미터는 미정 상태이므로 TC 단위화는 보류하고 그 사유를 `비고`에 기록한다.** 파라미터 확정 시 이 포인터가 가리키는 문서만 갱신하면 되고 본 지시서는 그대로 둔다.

전수 대상은 원문의 목차·번호·표 행을 **처음부터 끝까지 빠짐없이** 기록한다. ("중요한 것만 선별"은 전수 대상에 한해 금지.)

## 3. 커버리지 단위 메타데이터 기준 (Layer 1)

> **구분 범례:** `필수`=모든 단위에 반드시 채움 · `선택`=해당 시 채움(빈 값 허용) · `파생`=다른 컬럼/단계에서 계산 가능, 손 유지 비권장.

| 필드 | 구분 | 설명 | 예시 |
|---|---|---|---|
| `Unit ID` | 필수 | 커버리지 단위 고유 ID (표의 행 식별자) | `RC-HELP-SEC-001` |
| `type` | 필수 | 지식 유형 (OKF 필수 필드) | `Manual`, `Spec`, `TestCase`, `KnownIssue`, `HelpdeskArticle` |
| `title` | 필수 | 원천 문서 제목 | `RemoteCall 2단계 인증 사용 방법` |
| `description` | 선택 | 단위의 짧은 설명 | `관리자페이지에서 2단계 인증 설정 위치` |
| `product` | 필수 | 제품명 | `{PRODUCT}` |
| `feature` | 선택 | 기능명 | `2단계 인증` |
| `user_type` | 선택 | **독자 역할** (접근 권한 아님) | `관리자`, `상담원`, `고객`, `공통` |
| `acl_level` | 필수 | **접근 권한 등급 (거버넌스)** | `회사`, `본부`, `팀`, `파트`, `개인`, `공개` |
| `intent` | 선택 | 사용자 질문 의도 | `설정 방법 문의`, `오류 해결`, `가능 여부 확인` |
| `source/resource` | 필수 | 파일 경로 또는 URL | `{SOURCE_ROOT}매뉴얼/…pdf` 또는 `{HELPDESK_BASE}…` |
| `source_location` | 필수 | 원문 내 위치 (**단위 유일 식별 입도**) | `p.12 / 표2 / 3행`, `시트명!A23`, `본문 2단계 / 예외 b` |
| `related_units` | 선택 | **그룹 간/그룹 내 연결 Unit ID** (cross-group join) | `RC-SPEC-FUNC-014; RC-MANUAL-ADMIN-007` |
| `tags` | 필수 | 검색용 태그 | `RemoteCall, 보안, 2단계인증, 관리자페이지` |
| `citation_id` | 필수 | **골든셋이 이 단위를 근거로 지목할 때 쓰는 조인 키** | `RC-HELP-SEC-001` |
| `extracted_by` | 선택 | **생성자/모델** (union·dedup·충돌 판정 근거) | `난희`, `claude-opus`, `gpt-4o` |
| `confidence` | 선택 | **단위 추출 충실도** (상/중/하, ordinal) | `상`, `중`, `하` |
| `timestamp` | 선택 | 문서 기준일 또는 확인일 | `2026-06-23` |

> **`acl_level` (v0.2 신설, box 2 거버넌스):** OKF 명세에는 권한 모델이 없으므로 우리가 직접 부여한다. 5단계 ACL(회사→본부→팀→파트→개인) + 외부 공개(`공개`). Helpdesk 공개 문서는 보통 `공개`, 내부 사양서·TC는 최소 `회사` 이상. **출처 표시가 없으면 `{ACL_DEFAULT}`를 기본값으로 둔다.** `user_type`(누가 읽는 내용인가)과 `acl_level`(누가 접근 권한이 있는가)을 혼동하지 않는다.

> **`citation_id` (v0.2 정의 명확화):** 커버리지맵 안에서는 `Unit ID`와 **같다**(이 단위가 곧 자기 근거). 중복이 아니라 **다운스트림 조인 키**다. 골든셋 단계에서 질문 행은 자체 질문 ID를 갖고, `citation_id` 컬럼에 이 `Unit ID`를 적어 근거를 역참조한다.

> **`related_units` (v0.3 신설):** 그룹 간 연결을 Layer 1 메타데이터로 박는 컬럼. cross-group join을 사후 추론에 맡기지 않고 명시한다. 예: `RC-TC-WEBVIEWER-003`의 `related_units`에 그것이 검증하는 기능 단위 `RC-SPEC-FUNC-014`를 적고, `RC-KI-013`(이슈)에 그 이슈가 발생하는 절차 `RC-MANUAL-ADMIN-007`을 적는다. 여러 개면 `;`로 구분. 관계의 *종류*는 강제하지 않되(있음만 주장), 필요하면 `비고`에 한 줄 설명. 미상이면 비워둔다(빈 값 허용).
>
> **★ related_units 영속성 앵커 (v0.4):** related_units에 적는 Unit ID는 **표면 ID**이므로(6장 매핑 영속성 참조) 재분해 시 가리키던 타깃이 밀려 연결이 끊길 수 있다. 따라서 KI 매핑과 **동일 원칙**을 적용한다 — 영속 연결이 필요하면 (a) 대상의 source 키를 `비고`에 함께 적거나, (b) `(from source 키 → to source 키)` 별도 매핑 테이블로 관리한다. **순번 Unit ID는 표면 ID, 영속 신원은 source 키.** 코퍼스 동결(frozen) 상태에서만 작업한다면 bare Unit ID로 충분하나, 재분해가 예정되면 반드시 source 키 앵커를 둔다.

> **`extracted_by` / `confidence` (v0.3 신설, 병합용 provenance):** 다중 작업자/다중 모델 산출물을 합칠 때 쓰는 출처 정보다. `confidence`는 **이 단위가 원문 사실을 얼마나 충실히 담았는가(추출 충실도)** 를 뜻하며, 소비처는 세 곳뿐이다 — ① 충돌 tie-break(7장: 같은 source 키에 내용이 다른 단위가 겹칠 때 어느 쪽을 살릴지), ② 검수 우선순위(확신도 낮은 단위부터 사람 검토), ③ 상태값 보조 힌트(낮으면 `근거약함`/`사람확인` 후보 제안). 셋 다 대소 비교·정렬·분류 용도이고 **산술 연산이 없으므로 0~1 수치가 아니라 상/중/하(ordinal)로 적는다.** false precision(0.70 vs 0.72)을 피하고 작업자 간 일관성을 높이기 위함이다. ※ 골든셋 정밀본의 `confidence`는 **답변·문항 타당도**를 재는 별개 축이다. 커버리지맵 `confidence`(추출 충실도)와 측정 대상이 다르므로 더하거나 곱하지 않고, 표기 관례(상/중/하)만 맞춰 사람이 헷갈리지 않게 한다. 나중에 confidence-가중 점수나 numeric 게이트가 필요해지면 상=0.9 / 중=0.6 / 하=0.3 식으로 수치 승격한다(업그레이드가 다운그레이드보다 쉬움).

## 6. ID 부여 규칙 (3개 네임스페이스 정리)

세 가지 ID는 **서로 다른 네임스페이스**다. 혼동 금지.

| 종류 | 형식 | 소유 단계 | 예 |
|---|---|---|---|
| **Unit ID** (커버리지 단위) | `{PREFIX}-{SOURCE_TYPE}-{AREA}-{NUMBER}` | 커버리지맵 | `RC-HELP-SEC-001` |
| **Question ID** (골든셋 문항) | 골든셋 단계 자체 규칙 | 골든셋 | `RC-K01` (기존 KnownIssue 문항) |
| **OKF Concept ID** (파일 경로) | `.md` 뗀 번들 상대 경로 | OKF 번들(선택) | `security/two-factor-auth` |

Unit ID의 `SOURCE_TYPE-AREA` 예시:

| 원천 | Unit ID 예시 |
|---|---|
| 매뉴얼 / PC 지원 | `{PREFIX}-MANUAL-PC-001` |
| 매뉴얼 / 관리자 | `{PREFIX}-MANUAL-ADMIN-001` |
| 사양서 / 기능 | `{PREFIX}-SPEC-FUNC-001` |
| TC / 웹뷰어 | `{PREFIX}-TC-WEBVIEWER-001` |
| KnownIssue | `{PREFIX}-KI-001` |
| Helpdesk / 보안 | `{PREFIX}-HELP-SEC-001` |

> **★ KnownIssue ID 확정 (v0.3, A안):** 결정 규칙은 **"Unit ID 네임스페이스 = 원천 전수(source-driven), Question ID 네임스페이스 = 수요 기반(demand-driven)"** 이다. 이 규칙에 따라:
> - 커버리지 **단위** ID는 `{PREFIX}-KI-###`로 **신규 발급**한다(KnownIssue 원천을 전수 분해해 나오는 이슈/조건/영향/조치 단위마다 1개). 한 이슈가 질문 여러 개를 낳을 수 있고, 아직 질문이 없는 이슈(=미커버)도 단위 ID를 받아야 하므로, 단위 집합을 기존 질문 수에 묶지 않는다.
> - 기존 골든셋 **문항** ID(`RC-K01~K22`)는 별도 네임스페이스(Question ID)로 **그대로 둔다.** 질문 ID를 단위 ID로 승격(B안)하지 않는다 — 그러면 단위 집합이 수요에 묶여 전수·미커버 추적이 무너지고, 다른 4개 그룹과 ID 스킴이 어긋난다.
> - 둘을 잇는 매핑(`RC-K07` 문항 ↔ `RC-KI-013` 단위)을 골든셋 행의 `citation_id`에 기록한다.
>
> **★ 매핑 영속성 (v0.3):** RC-KI 번호는 재분해 시 밀릴 수 있는 **표면 ID**이므로, 매핑 테이블에는 RC-KI 번호만 적지 말고 **source 키(`source/resource` + `source_location`)를 함께 기록**한다(7장 dedup 키와 동일). 번호가 재배열돼도 source 키로 매핑을 재유도할 수 있어 cross-group join이 깨지지 않는다. 즉 순번은 표면 ID, **영속 신원은 source 키**다.

같은 문서 안에서는 위→아래 순서로 번호를 증가시킨다.

## 7. 중복/충돌 판정 기준 (v0.2 신설)

- **중복(dedup) 판정은 질문 텍스트가 아니라 `source/resource` + `source_location` (= source 키) 기준으로 한다.** 표현이 달라도 같은 출처 위치를 가리키면 중복으로 본다. 질문 문구가 비슷하다는 이유로 합치지 않는다(서로 다른 출처면 별개 단위). **단, `source_location`은 단위마다 유일하도록 충분히 세밀하게 적는다(2.1 참조) — 쪼갠 단위들이 같은 키로 묶여 잘못 dedup되는 것을 막는다.**
- **충돌**은 서로 다른 출처가 같은 사실에 대해 다른 값을 말할 때. 양쪽 Unit ID를 `비고`에 교차 기록하고 `충돌` 상태로 둔 뒤 사람확인으로 넘긴다. **같은 source 키에 내용이 다른 단위가 겹칠 때는 `extracted_by`/`confidence`(생성자·추출 충실도)를 1차 판단 근거로 삼아 어느 단위를 살릴지 정하고, 애매하면 `사람확인`으로 넘긴다.**
- 다중 모델/다중 작업자 산출물을 합칠 때는 **교집합이 아니라 합집합(union)** 으로 모은 뒤 위 source 키로 dedup한다.
- **★ dedup 발화 시점 (v0.4):** 2.1에서 source 키를 단위마다 유일하게 만들었으므로, **한 작업자·한 패스 안에서는 dedup이 구조상 발화하지 않는다**(키가 전부 다름). dedup은 **여러 작업자/모델 산출물을 union으로 합칠 때, 둘이 같은 source 키를 가리킨 경우에만** 작동한다. 따라서 단일 작업자가 "왜 중복이 안 잡히지?"라고 느끼는 것은 정상이며, 단위화 단계에서는 dedup을 기대하지 말고 병합 단계에서 적용한다.

## 8. (선택) OKF 번들 생성 기준 — Layer 2

본부장님이 OKF 위키로 서빙하라고 명시한 경우에만 생성한다. **단위가 아니라 엔티티 기준으로 파일을 만든다.**

### 8.1 디렉토리 = 엔티티 단위 파일
```text
{PREFIX-lower}/
├── index.md                 # 목차 (점진적 공개)
├── log.md                   # 변경 이력
├── install/
│   ├── index.md
│   ├── agent-install.md     # 엔티티 1개 = 커버리지 행 여러 개를 헤딩으로 수용
│   └── connection-error.md
└── security/
    └── two-factor-auth.md
```

### 8.2 개념 문서 = frontmatter + 구조화 본문
```markdown
---
type: HelpdeskArticle
title: RemoteCall 2단계 인증 사용 방법
description: 관리자페이지에서 2단계 인증을 설정하는 방법
product: RemoteCall
feature: 2단계 인증
user_type: 관리자
acl_level: 공개
intent: 설정 방법 문의
resource: https://help.remotecall.com/hc/ko/articles/…
tags: [RemoteCall, 보안, 2단계인증, 관리자페이지]
timestamp: 2026-06-23
---

# 기능 정의
# 사용 조건
# 절차            ← 커버리지 단위(절차 단계)들이 여기 헤딩으로 들어옴
# 예외/주의사항
# 답변 가능한 질문
# 관련 문서        ← 8.3 상호 링크
# Citations        ← 외부 출처(자기 Unit ID 아님)
```
- `type`은 OKF 유일 필수 필드. 본문은 산문보다 **헤딩·리스트·표** 같은 구조화 마크다운을 우선.

### 8.3 상호 링크 (ChatGPT 피드백 반영)
- 번들 루트 기준 **절대 링크 권장**: `[환경설정](/security/network.md)` — 파일이 이동해도 안정적.
- 링크는 "관계 있음"만 주장하고, 관계의 종류는 주변 문장이 설명한다. 깨진 링크는 허용(아직 안 쓴 지식일 수 있음).

### 8.4 `index.md` / `log.md` (예약 파일명)
- `index.md`: 디렉토리 내용 목차 + 미커버 영역 표시. frontmatter 없음.
- `log.md`: 최신이 위로 오는 날짜별 평탄 목록, 날짜 헤딩은 `YYYY-MM-DD`.
- 이 둘은 개념 문서로 쓸 수 없는 예약 파일명. 나머지 `.md`는 전부 개념 문서.

## 9. Helpdesk URL 처리 기준

Helpdesk 문서는 파일이 아니라 **웹 출처**로 취급한다. 각 URL을 다음으로 분해한다.
문서 제목 · 본문 안내 문장 · 절차 단계 · 조건/주의사항 · 수치/제한값 · 관련 문서 링크.
이미지에만 있는 정보는 `사람확인` 처리. URL은 반드시 `source/resource`에 기록한다.

13. **KnownIssue 단위가 `{PREFIX}-KI-###`로 발급되고, 기존 `RC-K##` 문항과의 매핑이 RC-KI 번호 + source 키로 함께 기록됐는가? (6장)**
14. **`related_units`로 cross-group 연결이 명시됐는가? (해당 단위에 한해) 재분해 예정이면 source 키 앵커를 두었는가? (3장)**

## 11. 사용 범위 및 다운스트림 공유 컬럼

이 문서는 주로 **커버리지맵 생성 작업**에 쓰지만, 아래 컬럼은 골든셋 생성·검증·RAG 평가 단계에서 계속 사용한다. 골든셋 생성자·검증자도 함께 참고하는 것이 좋다.

- `Unit ID` (골든셋의 `citation_id` 조인 대상)
- `source/resource`, `source_location` (source 키 — dedup·매핑 영속성의 기준)
- `acl_level` (RAG 응답 시 query-time ACL 필터의 입력)
- `related_units` (cross-group join 입력)
- `extracted_by`, `confidence`(상/중/하, 추출 충실도) — 충돌 tie-break·검수 우선순위·상태 힌트용. 골든셋 confidence(답변 타당도)와는 별개 축이며 표기만 맞춤.
- `citation_id`, `tags`, `상태`
