# 기획 정제 (Plan Refinement)

## 이 스킬이 하는 일

기획을 **정제**한다. "기획 전반"을 대신하는 스킬이 아니라, 딱 하나에 집중한다:

> 브리프·PRD·요구사항분석서 등 흩어진 기획 입력을 **종합하고, 충돌·누락·모호함을 점검하고, 정제된 단일 기획서로 수렴시킨다.**

두 가지 진입점을 모두 지원한다:

- **(A) 러프 → PRD**: 한 줄짜리 아이디어나 거친 브리프를 받아 구조화된 PRD로 다듬는다.
- **(B) 종합 → 정제**: 여러 기획 문서(브리프 + PRD + 요구사항분석서 등)를 받아 충돌을 점검하고 하나로 통합한다.

대부분의 실전 케이스는 둘이 섞여 있다 — 거친 입력 일부 + 정리된 문서 일부.

## 핵심 원칙

1. **수렴이 목적이다.** 결과물은 항상 *하나의* 정제된 기획서. 여러 문서를 늘어놓는 게 아니라 단일 진실원천(single source of truth)으로 합친다.
2. **충돌을 숨기지 않는다.** 입력 문서들이 서로 모순되면, 임의로 한쪽을 고르지 말고 충돌을 명시적으로 드러내고 결정을 요청한다.
3. **추측한 부분은 표시한다.** 입력에 없어서 채워 넣은 내용은 `[가정]` 태그로 명확히 구분한다.
4. **출처를 추적한다.** 정제된 요구사항이 어느 입력에서 왔는지 알 수 있게 한다.

## 워크플로우

### 1단계 — 입력 수집 및 분류

사용자가 준 모든 입력(파일 경로, 붙여넣은 텍스트, 구두 설명)을 모은다. 각 입력을 분류한다:

- **브리프**: 목적·배경·거친 방향
- **PRD**: 기능 요구사항, 사용자 스토리, 범위
- **요구사항분석서**: 상세 스펙, 제약조건, 비기능 요구사항
- **기타**: 디자인 노트, 기술 제약, 이해관계자 의견

입력이 한 종류뿐이고 거칠면 → **(A) 러프 → PRD 모드**로.
입력이 여러 개거나 정리된 문서가 섞여 있으면 → **(B) 종합 → 정제 모드**로.

### 2단계 — 분석

전체 입력을 읽고 다음을 추출한다:

- **목표(Goals)**: 이 기획이 이루려는 것
- **사용자/대상**: 누구를 위한 것인가
- **요구사항**: 기능(FR) + 비기능(NFR)으로 분리
- **범위(In/Out)**: 포함 / 명시적 제외
- **제약조건**: 기술·일정·리소스
- **미해결 질문**: 입력만으로 답할 수 없는 것

### 3단계 — 충돌·누락·모호함 점검 (이 스킬의 핵심)

다음 세 가지를 체계적으로 찾아낸다:

- **충돌(Conflicts)**: 두 입력이 서로 다른 것을 말함. 예) 브리프는 "모바일 우선", PRD는 데스크톱 레이아웃만 기술.
- **누락(Gaps)**: 필수인데 어느 입력에도 없음. 예) 에러 처리, 권한, 빈 상태(empty state), 성공 지표.
- **모호함(Ambiguity)**: 해석이 갈릴 수 있는 표현. 예) "빠르게", "많은 사용자", "직관적인".

발견한 항목을 표로 정리하고, **결정이 필요한 것은 사용자에게 묻는다**. 가능한 옵션을 제시한다 (AskUserQuestion 활용). 사소하고 기본값이 명백한 것은 `[가정]`으로 채우고 진행한다.

### 4단계 — 정제된 기획서 작성

아래 템플릿으로 단일 문서를 만든다. 기존에 PRD 형식이 있으면 그 형식을 따른다.

```markdown
# [제품/기능명] 기획서

## 1. 개요
- **목적**: (한 문단)
- **배경/문제**: 왜 지금 이게 필요한가
- **대상 사용자**:

## 2. 목표 및 성공 지표
- 목표:
- 성공 지표(측정 가능하게):

## 3. 범위
- **포함(In Scope)**:
- **제외(Out of Scope)**:

## 4. 기능 요구사항 (FR)
| ID | 요구사항 | 우선순위 | 출처 | 비고 |
|----|---------|---------|------|------|
| FR-1 | ... | Must/Should/Could | 브리프 | |

## 5. 비기능 요구사항 (NFR)
- 성능 / 보안 / 접근성 / 호환성 등

## 6. 사용자 플로우 / 시나리오
- (주요 흐름을 단계로)

## 7. 제약조건 및 가정
- 제약:
- **[가정]** 표시 항목:

## 8. 미해결 / 결정 필요 사항
- (4단계에서 사용자에게 못 받은 것 또는 후속 결정)

## 9. (선택) 스프린트/마일스톤 제안
- 요청 시, 요구사항을 우선순위 기반으로 단계 분할
```

### 5단계 — 검증 및 전달

- 정제된 기획서가 **모든 입력의 요구사항을 누락 없이** 담았는지 역추적 확인한다.
- 충돌이 모두 해소(또는 명시적으로 보류)됐는지 확인한다.
- 사용자에게 (1) 정제된 기획서, (2) 발견한 충돌·누락 요약, (3) 적용한 `[가정]` 목록을 함께 전달한다.

## 출력 위치

- 기본: 정제된 기획서를 마크다운 파일로 저장 (사용자가 경로를 주면 거기에, 아니면 프로젝트의 docs/ 또는 작업 폴더에).
- 사용자가 "보여만 줘"라고 하면 채팅으로만 출력.

## 하지 않는 것

- 코드 구현 (별도 작업)
- 디자인 목업 제작
- 임의로 충돌을 한쪽으로 봉합 (반드시 드러내고 묻는다)
