### 1) Keep — 잘된 점 / 유지할 것

**AI 활용 방식 / 모델 정보**
- 3권 분립 유지·강화: 출제(Claude) · 채점(Kimi k2.6) · 교차(Codex) + 결정은 사람. 자기 시험지 자기 채점 금지
- **이중판정 정착**: 답변 채점 488문항을 Kimi 정판정 × Claude 교차 검토 — 일치율 90.8%, 갈린 45건만 원문 대조로 확정. "AI 판정을 AI가 견제"하는 구조가 실전에서 작동
- **함정 면접**: 사람이 도메인(일본어)을 몰라도 채점관을 검증 — 정답을 아는 변조 답안 24개를 심어 23개 적발 확인 후에만 본채점 허용

**개발/업무 진행 방식**
- **앵커 문항 발명(이번 달 핵심)**: 시험지를 갈아엎으면서도 전 회차 문항 120개를 비공개로 재사용 — 회차 간 비교선 유지. "시험지를 개정하면 향상을 못 잰다"는 딜레마를 구조로 해결
- **양보다 검증 밀도**: r1(1,033문항, 양 위주)의 결함 경험 후 r2는 절반(488문항)으로 줄이고 문항마다 검증(발췌 원문 대조·유형 6종 고정·이중판정·캘리브레이션)을 걸음 — "각주 붙는 시험지"에서 "각주 없이 읽는 시험지"로. 488이면 오차 ±4%p 이내라 측정에 충분
- 향상 주장 규율: 잣대(시험지·채점기·임계값) 동결 비교에서만 "올랐다"고 말함. 신규 지표 첫 측정은 기준선이지 향상이 아님

**협업 방식**
- **"역지사지 회신" 정착**: 플랫폼에 성적만 던지지 않고 ① 수고 인정 → ② 실측 근거 → ③ 실험 방법 → ④ 탈출구("효과 없으면 버려도 됨") 구조로 회신 → 제안 3건이 전부 하루 안에 실험 로그로 회신되는 루프 형성
- 이견은 실측으로 해소: 옵션 실험(512자 상한)의 "차이 없음 → 불채택" 판단을 문항 짝지음 비교로 검증해 지지 · "대표 지표를 생성축으로" 제안을 데이터(1턴 검색 실패 213건 중 136건을 다회 검색 루프가 구제)로 실증해 수용

**생산성 향상 사례**
- 로그 도착 → 당일 채점 → 당일 다음 실험 지시: 6~7월의 회차당 수일 → **8월엔 하루 3회차**
- 진단 자동화: top_k=50 로그 1벌로 미적중 213건을 "회수 문제 57% / 순위 35% / 정밀도 8%"로 기계 분해 → 다음 개선의 조준점이 사람 판독 없이 나옴

**재사용 가능한 방법**
- **RAG 평가 표준 규격 v1 제정**: 측정 철학 5조 · 지표 체계 · 시험지 구성(앵커 20~30% 등) · 절차 관문(캘리브레이션·함정면접·이중판정·top_k 진단) · 오픈 게이트 골격 — 표준 본문은 불변, 제품별로는 **커스텀 협의 체크리스트 10항**(용도·통과선·플랫폼 구조·로그 형식·기밀 수준 등)만 발주자와 협의

### 2) Problem — 문제 / 부족했던 점

**기술적 문제**
- 판정기준서 파일이 폴더 이동으로 유실된 채 기본 기준서로 판정 진행(실측 불일치율은 낮아 결과 수용, 파일 복원 + 원장 기록으로 수습) — "규칙 파일의 소재도 검증 대상"이라는 교훈
- 관제판 범용 채점기가 신규 제품 로그를 잘못 채점 → 제품별 채점기 라우팅 가드 + 정지 프로세스 추가로 수습·재발 차단

**AI 활용 한계**
- LLM 채점관 간 판정 불일치 9.2%(45/488) — 문항 판정(1.7%)보다 답변 채점에서 크게 증가. 유도리(의미 동등) 판단은 채점관마다 갈림 → 이중판정 + 원문 대조 확정 절차가 필수임을 실증
- 다회 검색(ReAct)으로도 못 푸는 영역 실측: 자료 자체가 없으면 반복 검색해도 없고, 그때 지어냄(환각 6/41) — 검색 반복으로는 환각을 못 막는다

**협업 문제**
- 측정 대상 시스템의 내부 구조(다회 검색 루프 등)를 뒤늦게 인지 — 검색축만 재면 제품 반쪽 측정이 될 뻔함. 표준 체크리스트에 "플랫폼 구조 확인" 항목으로 편입

**일정 지연 원인**
- AI 세션이 구독 한도로 주기적으로 정지 → 이어달리기(체크포인트 승계)·계정 전환 승계·시간제 라운드로 흡수. 작업 상태를 AI의 기억이 아니라 저장소(원장·현황 브리핑)에 보관해, 세션이 끊기거나 계정을 바꿔도 새 세션이 같은 자리에서 즉시 계속(8월 실제 승계로 검증). 근본 해결은 용량 계획 필요

## 3. SSOT 관리현황

**SSOT 문서/자료 관리 방식**
- **원장(ledger.jsonl, append-only)이 유일 정본**: 모든 결정·수치·사유·사고를 5,500여 건 기록. "세션 기억"이 아니라 원장이 기억 — 어느 AI 세션이 와도 원장 재생으로 동일 상태 복원. 보고서의 어떤 수치든 원장으로 거슬러 올라가 재현 가능
- 이원 저장소: 관제판(파이프라인·도구) / 채점센터 금고(문항·정답·채점, 비공개 별도 저장소) — 정답키 무결성과 기밀을 저장소 경계로 보호
- 규칙의 정본: 판정기준서 v1.1 · 표준 규격 v1(orchestrator 루트) · 제품별 협의서 — 문서 위치를 CLAUDE.md 위치 지도에 등록해 세션이 자동 인지

**업데이트 주기 및 갱신 프로세스**
- 갱신은 사건 단위 즉시(작업 종료 훅이 자동 커밋·푸시 + 기밀 스캔 관문) — "나중에 정리"가 구조적으로 불가능
- 표준 규격은 "두 제품 이상에서 유효할 때만" 개정 — 버전 업 + 원장 기록 + 소급 여부 명시

**최신성 유지 (Drift 방지)**
- 관제 대시보드의 상태·성적 표시를 하드코딩에서 **산출물 파일 실측 자동 계산**으로 전환 — 화면과 실제가 어긋나는 drift를 원천 차단 (8월 실제 drift 2건 발견·수리)
- 인수인계 브리핑은 문서 저장이 아니라 **실행 시점 생성**(상태 파일+원장+프로세스 실측) — 낡을 수 없는 구조
