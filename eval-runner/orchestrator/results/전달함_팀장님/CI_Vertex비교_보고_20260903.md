## 0-1. "쉬운 질문에서는 Vertex가 더 정확하지 않나?" — 구획별 검증

같은 447문항을 "쉬움"의 여러 정의로 잘라 두 시스템의 답변 합격률을 비교했습니다 (새 응시 없음, 기존 채점 결과 재집계).

| 쉬움의 정의 | n | 자사 합격 | Vertex 합격 | Vertex 답변 지연 |
|---|---|---|---|---|
| 질문이 짧은 1/3 | 149 | **75.2%** | 56.4% | 3.9초 |
| 정답 필수요소 1개 | 103 | **78.6%** | 43.7% | 4.0초 |
| 정의형 (용어 뜻) | 25 | **92.0%** | 52.0% | 4.3초 |
| 양쪽 모두 검색 top5 적중 | 168 | **91.7%** | 72.0% | 4.0초 |
| **양쪽 모두 검색 1위 적중 (가장 쉬움)** | 55 | **98.2%** | 70.9% | 4.0초 |

- **어느 정의로 잘라도 자사가 앞섭니다.** 가장 쉬운 55문항(두 시스템 모두 정답 문서를 1위로 찾은 경우)에서도 자사 98.2% vs Vertex 70.9% — 같은 근거를 손에 들고도 Vertex 요약이 답을 만들지 못한 경우가 30%입니다.
- 문항 단위: Vertex만 합격 **28** · 자사만 합격 **142** · 둘 다 합격 206.
- Vertex 속도는 난이도와 무관하게 **약 4초로 일정** — 쉬운 질문이라고 더 빨라지지 않습니다(LLM 생성 시간이 지배적).
- 단서: 이 Vertex는 팀장님 청킹·기본 요약 설정입니다. Vertex 자체 청킹·요약 설정 조정(원본 문서 투입, 6절 (b))에서는 쉬운 문항 성적이 달라질 수 있습니다 — 그 실험 전까지 "쉬운 질문은 Vertex가 낫다"는 가설은 **현재 데이터로는 기각**됩니다.

## 0-2. 속도 — Vertex는 왜 저 속도가 나오고, 자사는 어떻게 올릴 수 있나

### Vertex 4.0초의 해부 (447문항 실측)

| 단계 | Vertex | 자사 (r4 형상, 31초) |
|---|---|---|
| 검색(하이브리드) | 0.24초 — 관리형 색인, 1회 호출 | 수 초 이내 (추정 — 서버 내부 측정 미제공) |
| 리랭크 | **없음** | **폭 50 · CPU ≈ 21초** (플랫폼 실측 역산: 폭10 14.2초 / 폭50 31.4초 → 폭당 선형) |
| 다회 검색(ReAct) | **없음 — 1턴 고정** | 최대 15턴, 턴마다 검색+LLM (턴별 시간 미제공) |
| 답변 생성(LLM) | **≈3.7초 (지연의 94%)** — 짧은 요약, 근거 5개 | 598자 중앙값 정돈 답변 (수 초) |
| 합계 | **4.0초 (P50) · 6.2초 (P95)** — 옵션 변경 판(리랭크+answer API) **5.8초 · 9.8초** | 31초 (P50, 서버 내부) |

Vertex가 빠른 이유는 단순합니다 — **정확도를 올리는 두 장치(리랭크·다회 검색)를 쓰지 않고, 한 번 검색해 바로 요약**하기 때문입니다. 그 대가가 검색 −16%p·답변 −26%p입니다. 즉 속도 격차와 품질 격차는 **같은 선택의 양면**이고, 자사가 속도를 올리는 길은 그 장치를 얼마나 덜 쓰느냐(A안) 또는 같은 장치를 얼마나 빠르게 돌리느냐(B안)로 갈립니다.

### A안 — Vertex 방향으로 맞춘다 (장치를 덜 쓴다)

| 조치 | 속도 효과 | 품질 위험 (실측·역산 기반, 예측 아님) |
|---|---|---|
| ReAct 15턴 → 1턴 | 턴 수만큼 절감 (턴별 실측 필요) | 1턴 실패 213건 중 ReAct가 구제한 **136건**을 잃음 → 미적중군 합격률 57%가 Vertex 수준(35%) 쪽으로 이동 |
| 리랭크 폭 50 → 10 (CPU) | 31 → 14초 | top5 62.6 → **52.3%** (운영 형상 실측치) |
| 리랭크 제거 | −14초 이상 | 미측정 — Vertex(리랭크 없음) 46.3%가 하한 참고 |
| 답변 짧게 | 생성 시간 비례 절감 | 필수요소 누락 위험 — 판정기준서상 부분/0점 증가 가능 |

- **도달 가능 속도**: Vertex와 같은 구조가 되므로 **4초대(답변 완료)**가 상한 참고치.
- **도달 가능 품질(역산 참고치, 가정 포함)**: 적중군 90%×281 + 미적중군을 ReAct 없는 수준(35~57% 사이)으로 두면 **약 63~68%**. Vertex 52%보다는 위, 현재 77.9%보다는 확실히 아래. **실측 전 가정치**입니다.
- 한 줄: **A안은 "우리 시스템으로 Vertex를 만드는 것"** — 속도는 따라가고 품질 우위의 상당 부분을 내놓습니다.

### B안 — 품질을 유지하며 속도를 올린다 (같은 장치를 빠르게)

| 조치 | 속도 효과 (역산) | 품질 영향 | 근거 |
|---|---|---|---|
| **① 리랭크 GPU화** (폭 50 유지) | **31 → 약 10초** (리랭크 21초 → ~1초) | **없음** — 같은 후보를 같은 순서로 | 플랫폼 확인 "GPU 시 약 1초" · 8/31 폭 실험 |
| **② ReAct 턴 상한** (15 → n) | 턴별 절감 | 상한 밖에서 구제되던 건만 손실 — **턴별 구제 분포 실측 필요** | 136건 구제가 몇 턴째에 났는지 로그 필드 요청 |
| **③ 스트리밍 (첫 글자 우선)** | **첫 글자 1~2초** 가능 — 검색 0.3초 + GPU 리랭크 1초 + LLM 첫 토큰 | **없음** — 답변 내용 동일, 보여주는 방식만 | Vertex 체감 속도의 정체가 이것 |
| ④ 검색 결과 먼저 표시 | 0.3초 내 | 없음 | UX |
| ⑤ 답변 길이 상한 | 생성 시간 비례 | 소폭 위험 — 필수요소 보존 규칙 병행 시 제한적 | r4 답변 중앙값 598자 |

- **도달 가능 속도**: ①만으로 **~10초(답변 완료)**, ①+②로 한 자릿수, ①+③으로 **첫 글자 1~2초**. 답변 완료 1~2초는 B안으로도 도달하지 않습니다 — Vertex도 4초입니다.
- **품질**: ①·③·④는 손실 0. ②·⑤는 실측 후 결정.
- 한 줄: **B안은 "지금 품질을 그대로 두고 시간을 사는 것"** — GPU 1대와 스트리밍 UX가 핵심이고, 둘 다 채점기로 품질 불변을 검증할 수 있습니다.

### 두 안을 가르는 질문 — "1~2초"의 정의

| 정의 | A안 | B안 | Vertex |
|---|---|---|---|
| ① 검색 결과 표시 | 0.3초 | 0.3초 | 0.24초 |
| ② 첫 글자 (스트리밍) | 1~2초 | **1~2초** (①+③) | 미측정 (스트리밍 API 별도) |
| ③ 답변 완료 | 4초대 | ~10초 → ReAct 상한 시 한 자릿수 | 4.0초 |

정의가 ①·②면 **B안으로 품질을 지키면서 1~2초에 도달**합니다. 정의가 ③이면 **어느 안도, Vertex도 1~2초는 아니며** 4초 vs 10초의 선택이 됩니다. 그래서 본부장님께 정의를 먼저 확정받는 것이 다음 설계의 전제입니다.

### 검증 방법 (표준 4장 — 예상 효과는 실측 후 확정)
- **B안 ①**: GPU 리랭크 형상 로그 1벌 → 같은 채점 → 품질 불변 확인 + 서버 내부 지연 병기 (로그에 `latency_ms` 필드 — 표준 후보 #1)
- **B안 ②**: ReAct 턴별 구제 분포 1회 실측 → 상한 n 결정
- **A안**: 1턴·폭 10·짧은 답 형상 로그 1벌 → 같은 채점 → 위 63~68% 가정치를 실측으로 대체
- 세 벌 모두 같은 488문항·같은 채점기라 **속도-품질 곡선 위에 점 3개**가 찍힙니다. 어디에 설지는 그 곡선을 보고 사업이 정합니다.

## 0-3. 비교 대상 — "Vertex"의 3계층 중 무엇과 비교했나

Google의 검색·RAG 제품군은 한 제품이 아니라 세 층입니다. **이번 비교 대상은 1열(Agent Search, 구 Vertex AI Search)** 입니다 — 이 보고서의 "Vertex"는 전부 이것을 뜻합니다.

| | **① Agent Search (구 Vertex AI Search)** ← 이번 비교 | ② Vertex AI RAG Engine | ③ 컴포넌트 DIY |
|---|---|---|---|
| 성격 | **완전관리형 검색엔진 + 생성 답변** — 켜면 바로 됨 | RAG 오케스트레이션 런타임 — 벡터DB·리랭커·모델을 골라 조립 | Layout Parser·Embeddings·Vector Search·Ranking·Grounded Gen API 직접 조립 |
| 조율 옵션 | **있음** — `answer` API의 추출형 답변·claim별 그라운딩 점수·임계값·저관련 폴백(`ignoreLowRelevantContent`)·모델 버전 고정·Ranking API 리랭커. **이번 실측에서는 이 중 하나도 켜지 않음**(구 `search`+`summary` 경로, `model=stable`) | 중간 | 높음 |
| 이 층과 비교하면 재는 것 | **"Google 기본값 제품 vs 우리 제품"** (제품 대 제품) | "우리가 Google 부품으로 얼마나 잘 만드나" (조율 실력 대 조율 실력) | 같음, 더 심함 |
| 데이터 상주 | global/us/eu (한국 없음) — 이번 global | 구성별 | 구성별 |

**왜 ①인가**: 미션의 문장이 "사용자의 눈높이가 Vertex만큼"입니다. 사용자가 경험하는 Vertex는 켜면 바로 답이 나오는 관리형 제품(①)이고, ②·③은 개발자가 조립하는 부품입니다. ②·③과 비교하면 Vertex의 실력이 아니라 **우리 조율 실력**을 재게 되어, 사실상 "Google 부품으로 자사 플랫폼을 다시 만드는 프로젝트"가 됩니다.

**②를 하려면**: Ranking API(리랭크)·Gemini 모델·청킹·임베딩 선택 후 수 회차 조율 → 별도 프로젝트 규모. 본부장님이 뜻한 "Vertex"가 ①(제품)인지 ②(Google 부품 RAG)인지 확정이 필요합니다 — ①이면 이번 비교가 답이고, ②면 범위를 다시 정합니다. 이번에 ①에서 쓰지 않은 부품(자체 청킹·Ranking API·고급 답변·스트리밍)을 켜는 6절 (b) 실험이 ①과 ② 사이의 중간 지점입니다.

## 6. 판단에 참고하실 것 (결정은 본부장님·플랫폼)

1. **품질**: 자사가 검색(+16%p)·환각(0 vs 3)에서 앞선다. 단 이는 리랭크 폭 50(GPU 전제)·ReAct·2단 판단 프롬프트의 결과이며, 운영 형상(폭 10·CPU)과 Vertex의 격차는 훨씬 작다.
2. **속도**: Vertex 기준 "답변 완료 4초·검색 0.24초". 자사가 1~2초에 가려면 **ReAct 턴 제한 + GPU 리랭크 + 스트리밍(첫 글자)** 이 필요하고, 그 형상의 품질은 **다시 재야** 한다(속도-품질 곡선의 새 점).
3. **정의 확정 요청**: "1~2초"가 ① 검색 결과 표시 ② 첫 글자 ③ 답변 완료 중 무엇인지. ①이면 자사 검색 단계 실측이 필요하고, ③이면 Vertex도 미달이다.
4. **다음 실험(제안)**: (a) 자사 "속도 형상"(ReAct 1턴·폭 50 GPU·짧은 답) 1벌 → 같은 채점 → 곡선의 새 점. (b-1) **옵션 변경 판 — 실측 완료(9/4)**: Ranking API + answer API(그라운딩 임계·저관련 폴백) + 모델 고정 → **66.4%**. 옵션 변경의 몫 = +14.1%p. (b-2) **자체 청킹 판** — 원본 문서를 Vertex에 투입해 파싱·청킹까지 Vertex 방식으로 → 검색 격차(47.7 vs 62.6)가 청킹 때문인지 확인하는 마지막 실험. 미실시
