# 통합 RAG 옵션 설계 명세서 v1.0

> **이 문서의 목적**
> 알피스(통합 RAG 지식 플랫폼)를 구축·운영할 때 설정해야 하는 **모든 옵션**을 한 곳에 정리한 문서입니다.
> 각 옵션이 **① 무엇을 위한 것인지 ② 왜 필요한지 ③ 골든셋(평가) 어디와 연결되는지 ④ 통합 RAG 안에서 어떤 역할인지**를
> 함께 설명합니다. RAG를 처음 접하는 사람도 이 문서 하나로 전체 그림을 이해할 수 있도록 작성했습니다.

---

## 0. 먼저 — RAG가 뭐고, 왜 옵션이 중요한가

**RAG(검색 증강 생성)** 는 한마디로 **"오픈북 시험을 보는 AI"** 입니다.
AI가 머릿속 지식으로만 답하면 회사 내부 사정을 모르고 지어냅니다(환각). 그래서 답하기 전에
**회사 문서를 먼저 찾아보고(검색)**, 그 내용을 근거로 **답을 만듭니다(생성)**. 이 "찾아보고 답하는" 전체 과정이 RAG입니다.

문제는 — **"어떻게 찾고 어떻게 답하느냐"에 따라 정확도가 크게 갈립니다.**
- 문서를 너무 크게 자르면 → 엉뚱한 부분까지 딸려와 답이 흐려짐
- 너무 잘게 자르면 → 문맥이 끊겨 답을 못 만듦
- 검색 결과를 너무 적게 주면 → 정보 부족, 너무 많이 주면 → 노이즈로 환각

그래서 **옵션(설정값)이 곧 RAG의 품질**입니다. 이 문서는 그 옵션들을 단계별로 정리한 것입니다.

### 골든셋(평가)과의 관계 — 왜 함께 봐야 하나

**옵션을 바꾸면 정확도가 바뀌는데, "정확도가 올랐는지"를 어떻게 아느냐** — 그걸 재는 자(尺)가 **골든셋**입니다.
골든셋은 "정답이 정해진 시험 문제 모음"이고, 옵션을 바꿀 때마다 이 시험을 다시 쳐서 점수를 비교합니다.

```
   옵션 변경  ──►  RAG 시스템  ──►  골든셋으로 채점  ──►  점수 비교  ──►  최적 옵션 결정
   (이 문서)      (팀이 구축)       (평가 체계)          (리더보드)
```

즉 **이 옵션 문서와 골든셋은 한 쌍**입니다. 옵션은 "조절 손잡이", 골든셋은 "그 손잡이를 돌렸을 때 좋아졌는지 알려주는 계기판"입니다.

## 1. 통합 RAG 전체 구조 (7박스)와 이 문서의 범위

알피스는 7개 기능 블록으로 구성됩니다. 이 문서가 다루는 옵션은 그중 **2·5·6·7번**에 해당합니다.

| 박스 | 역할 | 이 문서에서 다루는 옵션 |
|------|------|----------------------|
| 1 | AI LLM (모델 자체) | (범위 외) |
| **2** | **데이터 체계·권한** | 4단계 권한 필터 |
| 3 | 사용자 제품(화면) | (범위 외, 단 8장에 UI 예시) |
| 4 | 기반기술 필터(유해·민감) | 5단계 가드레일(일부) |
| **5** | **AI Agent(판단·라우팅)** | 5단계 생성, 6단계 질의분해 |
| **6** | **지식 파이프라인(검색)** | 1·2·3단계 (청킹·검색·리랭킹) |
| **7** | **평가 체계** | 7단계 평가 지표 |

**RAG 파이프라인 흐름** (위에서 아래로):

```
문서 입력
   │
   ▼
[1단계] 청킹      문서를 검색 가능한 조각으로 자름           ← 박스 6
   │
   ▼
[2단계] 검색      질문에 맞는 조각을 가져옴                  ← 박스 6
   │
   ▼
[3단계] 리랭킹    가져온 조각의 순위를 다시 매김             ← 박스 6
   │
   ▼
[4단계] 권한필터  질문자가 볼 수 있는 것만 남김              ← 박스 2 ★
   │
   ▼
[6단계] 질의분해  복잡한 질문을 쪼갬(필요시)                 ← 박스 5
   │
   ▼
[5단계] 생성      LLM이 최종 답을 만듦                       ← 박스 5
   │
   ▼
[7단계] 평가      답이 맞는지 골든셋으로 채점                ← 박스 7 ★
```

## 2. ⚠️ 가장 먼저 알아야 할 것 — 되돌릴 수 없는 옵션

> ## ╔════════════════════════════════════════════════════════════╗
> ## ║  ⚠️  청킹 방식(1단계)은 한 번 정하면 변경할 수 없습니다.     ║
> ## ╚════════════════════════════════════════════════════════════╝

**왜 중요한가:** 청킹은 문서를 잘라 벡터(숫자)로 변환해 저장하는 작업입니다. 한 번 저장하면
그 방식이 데이터에 고정되어, 바꾸려면 **전체 문서를 삭제하고 처음부터 다시 인덱싱**해야 합니다.
문서가 수만 건이면 시간·비용이 큽니다.

**그래서 실무 규칙:**
1. 청킹 방식은 **저장 전에 골든셋으로 먼저 실험**해서 결정한다 (4장 참조)
2. 나머지 옵션(검색 수·리랭킹·생성)은 **저장 후에도 자유롭게 변경 가능** → 운영 중 튜닝
3. 관리자 화면에서 청킹 단계에는 반드시 **변경불가 경고**를 표시한다 (8장 UI)

| 옵션 | 변경 가능 여부 | 시점 |
|------|-------------|------|
| 1단계 청킹 | ❌ **불가** (재인덱싱 필요) | 구축 시 신중히 |
| 2단계 검색 수·방식 | ✅ 가능 | 운영 중 언제든 |
| 3단계 리랭킹 | ✅ 가능 | 운영 중 언제든 |
| 4단계 권한 필터 | ✅ 가능 | 운영 중 언제든 |
| 5·6단계 생성·분해 | ✅ 가능 | 운영 중 언제든 |

## 3. 단계별 옵션 상세

각 옵션마다 **[무엇을] [왜 필요] [선택지·값] [골든셋 연결]** 순으로 설명합니다.

### [1단계] 청킹 — 문서를 어떻게 자를 것인가  (박스 6)

**무엇을:** 긴 문서를 검색·임베딩이 가능한 작은 조각(chunk)으로 나누는 작업.
**왜 필요:** AI는 문서 전체를 한 번에 못 봅니다. 조각으로 나눠 그중 질문에 맞는 것만 찾아야 합니다.
잘리는 방식이 검색 정확도의 **가장 근본**입니다.

#### chunkingStrategy — 청킹 방식 (5종)

| 값 | 설명 | 세부 파라미터 | 언제 쓰나 |
|------|------|------------------|----------|
| `NONE` | 안 자름 | 없음 | 이미 짧게 정리된 문서 |
| `FIXED_SIZE` | 토큰 수로 기계적 절단 | `maxTokens`(512), `overlapPercentage`(20) | 길이 균일한 단순 문서 |
| `HIERARCHICAL` | 부모(큰)+자식(작은) 2층 | `maxPare[기밀마스킹]okenSize`(1500), `maxChildTokenSize`(300), `overlapTokens`(60) | **표·대중소 분류 문서 ★RC 권장** |
| `SEMANTIC` | 의미 바뀌는 곳에서 절단 | `maxTokens`(300), `bufferSize`(1), `breakpointPercentileThreshold`(95) | 불규칙한 긴 글 |
| `CUSTOM_LAMBDA` | Lambda 함수로 직접 구현 | Lambda ARN 지정 | 위 4종으로 안 될 때 완전 커스텀 |

**파라미터 설명:**
- `maxTokens` / `maxPare[기밀마스킹]okenSize` / `maxChildTokenSize`: 조각 크기. 클수록 문맥 풍부, 작을수록 정밀하나 끊김 위험. 예: `300` `512` `1024` `1500`
- `overlapPercentage` / `overlapTokens`: 앞뒤 조각이 겹치는 정도. 문장이 경계에서 잘려 의미를 잃는 걸 방지. 예: `10` `20`(%)
- `breakpointPercentileThreshold`: 의미 변화 민감도(높을수록 촘촘히 자름)

#### parsingStrategy — 파싱 방식

| 값 | 설명 |
|------|------|
| `BEDROCK_DATA_AUTOMATION` | 표·이미지·PDF를 AI가 해석해 텍스트로 변환. 정확하나 비용 발생 |
| `FOUNDATIONAL_ROUTING` | 일반 텍스트 추출. 빠르고 저렴하나 표·이미지 해석 약함 |

- **multimodal 파싱 모델**: `BEDROCK_DATA_AUTOMATION` 선택 시 사용할 AI 모델 지정
  - `anthropic.claude-3-5-sonnet` — 표·복잡한 PDF에 정확
  - `anthropic.claude-3-haiku` — 빠르고 저렴, 단순 문서용

#### embeddingModelArn — 임베딩 모델

문서 조각을 숫자(벡터)로 변환할 때 쓰는 모델. **한국어 지원 여부가 핵심.**

| 모델 | 특징 |
|------|------|
| `amazon.titan-embed-text-v2:0` | AWS 기본. 영어 중심 |
| `cohere.embed-multilingual-v3` | **다국어(한국어) 지원 ★알피스 권장** |
| `amazon.titan-embed-image-v1` | 이미지·텍스트 혼합 임베딩 |

**골든셋 연결:**
- (에디션별 세부 수치를 물어 자식 조각만으로는 답 못하고 부모 문맥이 함께 와야 정답이 되는지 검증) → **HIERARCHICAL 청킹이 작동하는지 보는 시험**
- (대명사·지시어 질문으로 앞뒤 조각이 함께 와야 지칭 대상을 알 수 있는지 검증) → **overlap이 충분한지 보는 시험**

### [1-2단계] 벡터스토어 — 임베딩된 조각을 어디에 저장할 것인가  (박스 6)

**무엇을:** 임베딩(숫자 변환)된 문서 조각을 저장하고 검색하는 데이터베이스.
**왜 필요:** 질문이 들어오면 이 저장소에서 "비슷한 조각"을 빠르게 찾아옵니다. 선택에 따라 비용·속도·확장성이 다릅니다.

| vectorStoreType 값 | 설명 | 특징 |
|------|------|------|
| `OPENSEARCH_SERVERLESS` | AWS 관리형 검색 엔진 | 서버리스, 설정 간단. 비용 ~$701/월~ |
| `PINECONE` | 전용 벡터 DB SaaS | 벡터 검색 특화, 외부 서비스 |
| `REDIS` | 인메모리 캐시 기반 벡터 저장 | 빠름, 소규모 적합 |
| `RDS` (pgvector) | AWS RDS PostgreSQL + pgvector 확장 | 비용 저렴(~$30/월~), 기존 RDB와 통합 |
| `MONGO_DB_ATLAS` | MongoDB 클라우드 벡터 검색 | 문서DB 기반, 유연한 스키마 |

**알피스 관점:** 온프레미스·비용 민감 환경이면 `pgvector(RDS)`, AWS 완전 관리형이면 `OPENSEARCH_SERVERLESS` 권장.

---

### [2단계] 검색 — 무엇을 몇 개 가져올 것인가  (박스 6)

**무엇을:** 질문이 들어오면 저장된 조각 중 관련 있는 것을 꺼내오는 단계.
**왜 필요:** LLM에게 줄 "참고 자료"의 양과 방식을 정합니다. 이게 답의 재료가 됩니다.

| 옵션 | 값 | 기본값 | 의미 |
|------|------|--------|------|
| `numberOfResults` | 숫자 | 5 | LLM에 줄 참고 조각 수. 예: `5` `10` `20`. ↑정보풍부/노이즈증가 ↓빠름/누락위험 |
| `overrideSearchType` | `SEMANTIC` / `HYBRID` | KB 기본 | 검색 방식 |

- **`SEMANTIC`**: 의미가 비슷한 것을 찾음 (예: "컴퓨터 조종" → "원격 제어")
- **`HYBRID`**: 의미 + 키워드를 동시에 찾음. **모델명·에러코드·조항번호처럼 정확한 글자가 중요할 때 필수**

**filter — 메타데이터 필터 (권한 구현 핵심):**

| 연산자 | 예시 | 용도 |
|------|------|------|
| `equals` / `notEquals` | 부서=인사팀 | 특정 부서 문서만 |
| `greaterThan` / `lessThan` | 보안등급 ≤ 2 | 등급 범위 제한 |
| `in` / `notIn` | 부서 ∈ [영업, 마케팅] | 복수 부서 |
| `startsWith` | 문서코드 시작값 | 특정 시리즈 |
| `andAll` / `orAll` | 조건 조합 | 복합 권한 |

**실무 팁:** `numberOfResults`는 5로 시작하고, 답변 실패가 잦으면 10으로 올립니다(응답 시간 약 1초 증가 감수).

**골든셋 연결:**
- (모델명·에러코드를 오타나 한글 발음으로 물어, 의미검색만으로는 못 잡는 걸 HYBRID가 잡는지 검증) → **검색 방식(HYBRID) 시험**
- (복합 질문에서 여러 조각이 다 필요할 때 numberOfResults가 충분한지 검증)

### [3단계] 리랭킹 — 가져온 것의 순위를 다시 매김  (박스 6)

**무엇을:** 2단계에서 가져온 조각들의 순위를, 더 정밀한 모델로 한 번 더 재정렬.
**왜 필요:** 벡터 검색은 "대충 비슷한 것"을 가져와서, **비슷해 보이지만 틀린 문서(낚시 문서)**가
상위에 올 수 있습니다. 리랭커가 "진짜 관련 있는 것"을 위로 올려줍니다.

| 옵션 | 값 | 기본값 | 의미 |
|------|------|--------|------|
| `rerankingConfiguration` type | `BEDROCK_RERANKING_MODEL` | off | 재정렬에 사용할 모델 방식 |
| `numberOfRerankedResults` | 숫자 | 5 | 재정렬 후 최종 남길 수 |

**권장 흐름:** 2단계에서 넉넉히(10개) 가져온 뒤 → 리랭커가 진짜 관련 5개로 압축 → LLM 전달.
노이즈가 줄어 답이 정확해집니다. 단 **비용·시간이 늘어납니다.**

**골든셋 연결:**
- (버전별·OS별로 제목은 비슷하나 내용이 다른 낚시 문서 환경에서, 딱 맞는 버전이 1위로 오는지 검증) → **리랭킹이 작동하는지 보는 시험**

---

### [4단계] 권한 필터 — 누가 무엇을 볼 수 있나  ★박스 2

**무엇을:** 질문자의 권한에 따라, 볼 수 있는 문서 안에서만 검색하도록 거르는 단계.
**왜 필요:** 인사팀 대외비를 일반 직원이 검색하면 안 됩니다. **권한이 RAG 검색 단에서 적용**되어야
보안이 지켜집니다. 알피스의 핵심 차별점(2번 박스)입니다.

위 [2단계] 검색의 `filter` 연산자(`equals` `in` `andAll` 등)가 권한 구현 도구입니다.

**권한 모델:** 회사 > 본부 > 팀 > 파트 > 개인 (상위가 하위를 포함).
권한 밖 문서는 **검색 결과에서 원천 제외**됩니다(답에 섞이면 안 됨).

**골든셋 연결:**
- (권한이 없는 보안 문서 내용이 답변에 조금이라도 섞이면 실패 0점 — 가장 엄격한 게이트 항목) → **권한 필터가 작동하는지 보는 시험**

> **참고:** 이 옵션은 "권한별로 다른 문서 세트"가 있어야 검증됩니다. 공개 매뉴얼(예: 제품 매뉴얼)만
> 있는 단계에서는 검증 대상이 없어 **PASS(해당 없음)** 로 두고, 실제 사내 데이터(부서별 접근 문서)가
> 연결되면 활성화합니다.

---

### [5단계] 생성 — LLM이 답을 만드는 방식  (박스 5)

**무엇을:** 검색된 근거를 바탕으로 LLM이 최종 답변을 작성하는 단계.
**왜 필요:** 같은 근거라도 어떻게 답하게 하느냐(형식·길이·일관성)를 정합니다.

| 옵션 | 기본값 | 의미 |
|------|--------|------|
| modelArn | — | 생성 모델 선택 |
| promptTemplate | — | 답변 형식·톤 지정 프롬프트 |
| temperature | 0 | 0=일관된 답, ↑=창의적. **평가 시엔 0 권장**(재현성) |
| topP | 1 | 확률 누적 컷 |
| maxTokens | — | 답변 최대 길이 |
| guardrail | — | 유해·민감정보 필터 (박스 4 영역) |

**골든셋 연결:**
- 모든 생성 품질 지표(7단계)가 여기 영향을 받음. 특히 temperature=0이어야 같은 질문에
  같은 답이 나와 **채점의 재현성**이 보장됨

---

### [6단계] 질의 재작성 — 복잡한 질문 분해  (박스 5)

**무엇을:** 한 문장에 여러 질문이 섞였을 때, 각각으로 쪼개 검색한 뒤 종합.
**왜 필요:** "A의 예산과 B의 진행상황 비교" 같은 질문은 한 번 검색으로는 한쪽만 답하기 쉽습니다.

| 옵션 | 기본값 | 의미 |
|------|--------|------|
| queryReformulation on/off | off | 켜면 복합 질문을 하위 질의로 분할 |

**골든셋 연결:**
- **RAG-05 (다중 조건 복합 질문):** 두 정보가 답에 **모두 누락 없이** 포함되는지 검증

---

### [7단계] 평가 — 잘 작동하는지 채점  ★박스 7

**무엇을:** 위 옵션들이 실제로 좋은 답을 만드는지 골든셋으로 채점하는 단계.
**왜 필요:** 옵션을 바꿨을 때 "정말 좋아졌는지"를 객관적 점수로 확인해야 합니다. 채점은 LLM-as-Judge(채점관 AI)가 수행.

#### evaluatorModelIdentifier — Judge 모델

채점을 수행할 AI 모델의 ARN을 지정합니다. Bedrock에서 사용 가능한 모델만 가능.
- 예: `anthropic.claude-3-5-sonnet` (정밀 채점용)
- 예: `anthropic.claude-3-haiku` (빠른 채점, 비용 절감)
- **우리 제약**: Anthropic API 키 없음 → Kimi API(`kimi-k2-0905-preview`) 기반으로 Judge 설계

#### 내장 메트릭 (Builtin)

| 메트릭 | 값 | 의미 |
|------|------|------|
| 정확도 | `Builtin.Accuracy` | 정답과 일치하는가 |
| 충실도 | `Builtin.Faithfulness` | 검색 근거만 썼나 = **환각 감지 게이트** |
| 관련성 | `Builtin.Relevance` | 가져온 문서가 질문과 관련 있나 |
| 완전성 | `Builtin.Completeness` | 빠뜨린 내용 없나 |

**추가 지표 (책임 AI):**
- Harmfulness: 유해 내용
- Answer Refusal: 거절이 적절한가 (함정 질문 연결)
- Stereotyping: 편향

**핵심 기능:** 위 1~6단계 옵션(청킹·임베딩·검색수·리랭커 등)만 바꿔가며 **같은 골든셋으로 점수를 비교**할 수 있습니다.
→ "어떤 옵션 조합이 우리 데이터에 최적인가"를 실험으로 증명. 이것이 7번 평가 체계의 실제 용도입니다.

---

## 4. 옵션과 골든셋의 연결 한눈에 보기

각 옵션이 어떤 골든셋 규칙으로 검증되는지 정리한 표입니다. **옵션은 손잡이, 골든셋 규칙은 그 손잡이의 계기판**입니다.

| 단계 | 옵션 | 검증하는 골든셋 규칙 | 무엇을 확인 |
|------|------|-------------------|------------|
| 1 청킹 | 계층형 여부 | RAG-01 계층 결합 | 부모 문맥이 함께 오는가 |
| 1 청킹 | overlap | RAG-02 전후 문맥 | 인접 문맥이 끊기지 않나 |
| 2 검색 | HYBRID | RAG-07 고유명사·코드 | 정확한 텍스트를 찾나 |
| 2 검색 | numberOfResults | RAG-05 복합 질문 | 충분히 가져오나 |
| 3 리랭킹 | on/off | RAG-09 유사 노이즈 | 낚시 문서를 거르나 |
| 4 권한 | 메타데이터 필터 | RAG-03 권한 필터링 | 권한 밖 문서를 막나 (PASS 가능) |
| 5 생성 | temperature=0 | (전체 재현성) | 같은 질문에 같은 답 |
| 6 분해 | queryReformulation | RAG-05 복합 질문 | 쪼개서 다 답하나 |
| 7 평가 | 지표 선택 | 전체 | 위 모두를 점수화 |

> **PASS 규약:** 어떤 옵션을 검증할 데이터가 자료에 없으면(예: 권한별 문서가 없으면 RAG-03),
> 해당 골든셋 항목은 PASS(해당 없음)로 두고 데이터가 생기면 활성화합니다. 억지로 만들지 않습니다.

---

## 5. 통합 RAG 안에서의 상관관계 — 왜 한 덩어리인가

이 옵션들은 따로 노는 게 아니라 **사슬처럼 연결**됩니다. 한 단계의 선택이 다음 단계에 영향을 줍니다.

```
[청킹] 잘게 자르면 ──► [검색] 더 많이 가져와야(numberOfResults↑) ──► [리랭킹] 노이즈 압축이 더 중요
   │                                                                          │
   └─ 크게 자르면 ──► 적게 가져와도 됨 ──► 단 부모 문맥 큰 계층형이 유리       │
                                                                              ▼
                              [권한] 가져온 것 중 볼 수 있는 것만 ──► [생성] 근거로 답 ──► [평가] 채점
```

**예시로 보는 상관관계:**
- 청킹을 잘게(자식 300토큰) 했는데 검색을 5개만 하면 → 문맥이 부족해 답이 빈약 → 평가에서 Completeness 하락
- 검색을 20개로 늘렸는데 리랭킹을 끄면 → 노이즈가 많아 → 평가에서 Faithfulness 하락(환각)
- 권한 필터를 안 걸면 → 보안 문서가 답에 섞임 → RAG-03에서 즉시 0점

**그래서 "최적 옵션"은 하나의 정답이 없고, 우리 데이터·질문 유형에 맞춰 조합을 찾아야 합니다.**
그 조합 찾기를 가능하게 하는 도구가 골든셋(7번)입니다. **옵션(6·2·5번)과 평가(7번)는 한 몸**입니다.

## 6. 사용자별 화면 설계 — 옵션을 누구에게 보여줄 것인가

**핵심 원칙:** 옵션을 아무에게나 노출하면 안 됩니다. **권한에 따라 만질 수 있는 옵션을 나눕니다.**

### 6-1. 왜 옵션을 다 주면 안 되는가 — 두 가지 위험

옵션을 모든 사용자에게 열어두면 두 가지 문제가 생깁니다.

1. **사고 위험.** 청킹(1단계)은 한 번 잘못 누르면 전체 문서를 다시 인덱싱해야 합니다.
   일반 직원이 멋모르고 누르면 시스템이 멈춥니다. **되돌릴 수 없는 옵션은 아무에게나 주면 안 됩니다.**
2. **보안 위험 (더 치명적).** 권한 필터(4단계)를 사용자가 직접 끄거나 바꿀 수 있다면,
   일반 직원이 "권한 필터 끄기"로 대외비를 열어볼 수 있습니다.
   **권한 설정을 권한 없는 사람이 만지는 것은 보안의 자기모순**입니다. 절대 열면 안 됩니다.

그래서 옵션을 숨기는 것은 **불친절이 아니라 배려이자 보안**입니다. 일반 직원이 원하는 것은
"청킹 토큰 수"가 아니라 "질문하면 정확한 답"이기 때문입니다.

### 6-2. 누가 무엇을 만지는가 — 3단계 권한 분리

| 옵션 | 시스템 관리자 | 부서 관리자 | 일반 사용자 |
|------|:---:|:---:|:---:|
| 1단계 청킹 (변경불가) | ✅ 설정 | ❌ | ❌ |
| 2단계 검색 수·방식 | ✅ 기본값 | 🔸 부서 범위 조정 | ❌ |
| 3단계 리랭킹 | ✅ | 🔸 | ❌ |
| 4단계 **권한 필터** | ✅ 정책 수립 | 🔸 부서 범위 내 | ❌ **절대 불가** |
| 5단계 생성(프롬프트·톤) | ✅ | 🔸 부서 맞춤 | ❌ |
| 6단계 질의 분해 | ✅ | ❌ | ❌ |
| 검색·질문하기 | ✅ | ✅ | ✅ |
| 피드백(👍👎·오답신고) | ✅ | ✅ | ✅ |

- **시스템 관리자**: 전사 기준을 정함. 청킹·전사 권한 정책 등 되돌리기 어려운 것 전담.
- **부서 관리자(중간 단계, 선택)**: 알피스 권한 모델(회사>본부>팀>파트)과 맞물려,
  **자기 부서 범위 안에서만** 검색 수·프롬프트 톤 등을 조정. 전사 설정(청킹 등)은 잠겨 있음.
  이 단계를 두면 중앙이 모든 요청을 떠안지 않고 부서가 자율성을 가짐.
- **일반 사용자**: 실제로 할 수 있는 것은 **질문하기 + 피드백** 둘뿐. 나머지 옵션은 모두 숨김.

> **한 줄 원칙:** 되돌릴 수 없는 것(청킹)과 보안에 관한 것(권한 필터)은 일반 사용자에게 절대 노출하지 않는다.

청킹 단계엔 경고 박스를 최상단에 둡니다. 전사 권한 정책도 여기서만 수립합니다.

## 7. 요약 — 이 문서가 말하는 것

1. RAG는 "찾아보고 답하는 AI"이고, **옵션이 곧 품질**이다.
2. 옵션은 7단계로 나뉘며, 알피스가 다루는 건 **2·5·6·7번** 박스다.
3. **청킹(1단계)만 변경 불가** — 구축 전 골든셋으로 실험해 신중히 정한다. 나머지는 운영 중 조정 가능.
4. 모든 옵션은 **골든셋의 특정 규칙(RAG-01~11)으로 검증**된다 — 옵션은 손잡이, 골든셋은 계기판.
5. 옵션들은 **사슬처럼 연결**되어, 최적 조합은 데이터·질문 유형에 따라 골든셋으로 찾아야 한다.
6. 옵션은 **권한에 따라 3단계로 나눠** 노출한다 — 시스템 관리자(전사·청킹·권한정책) / 부서 관리자(자기 부서 범위) / 일반 사용자(질문·피드백만). 되돌릴 수 없는 청킹과 보안에 관한 권한 필터는 일반 사용자에게 **절대 노출하지 않는다.**

> 한 문장 결론: **옵션(2·5·6번)을 조절하고 → 골든셋(7번)으로 점수를 재고 → 최적값을 찾는다.
> 이 순환이 통합 RAG의 품질을 만든다.**
